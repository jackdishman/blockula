# Blockula mainnet design (protocol v1)

This is the contract for closing the blockers in [MAINNET.md](MAINNET.md). It records the decisions, specifies every consensus-format change, and splits the work into packages. Where it and older docs disagree, this file wins; PLAN.md and MAINNET.md are updated as packages land.

Mainnet is a **new chain**. Nothing here has to replay the current public testnet (`blockula-testnet`, v0.4.x): that chain keeps running its own binary until it's replaced by a testnet on protocol v1. So legacy compatibility branches (for example in the state root) are removed, not extended.

## 2. Engineering rules (every package)

- **Determinism.** No floats, wall clocks, randomness or `HashMap` iteration order in anything that touches state or block validity. Products use `u128`. Every new state record has a canonical binary encoding and is covered by the state root.
- **Accounting.** All balance changes go through the journaled helpers. `State::check_invariants()` (supply = Σ balances + escrows + stakes + pool; no negative or orphaned records) must hold after every block in tests and the simulator.
- **Parity.** Every tx type has identical signing bytes in `node/src/types.rs` and `sdk-ts/src/tx.ts`, a shared vector test on both sides, `check_format` bounds, and a plain-English `describe()` summary.
- **Tests.** `cargo test --manifest-path node/Cargo.toml` passes; consensus-touching work adds a simulator scenario; SDK-touching work passes `npm run build -w @blockula/sdk` and the e2e against `blockula dev`.
- **Style.** Match the surrounding code: concise, doc comments on public items, the same comment density, no new frameworks where a helper will do.
- **Scope.** Stay inside your package's files unless the spec says otherwise. Never touch live infrastructure (Fly, npm, GitHub settings), never push.

## 3. Protocol v1 specification

### 3.1 Transactions (Tx v3)

```
Tx { chain_id, genesis_hash, from, nonce, fee, tip, valid_until, action, memo, public_key, signature }
```
- Signing bytes: domain `BLOCKULA_TX_V3`, then `chain_id`, `genesis_hash` (32 raw bytes), `from, nonce, fee, tip, valid_until`, the action tag and fields, `memo`.
- `genesis_hash` is the digest of the chain's genesis block (`/api/status`), so a tx names the chain *instance*, not just its id: a relaunch that keeps the id (a re-summoned testnet) is another chain, and txs signed on the old one don't replay on it (audit #7). Admission, gossip and block verification check it statelessly with `chain_id` (`check_tx_stateless`); `Wallet.build` fills it in from `/api/status`, offline signers pass it.
- `fee` is the most the sender will pay. The tx is charged `base_fee(height) × size + tip`, which must be ≤ `fee`; the base part is burned, the tip goes to the proposer. Until 3.6 lands, `base_fee × size` is `min_fee(size)`.
- The tip is a payment, not a burn (audit F01): it is at most `tip_cap_multiple` (20 at genesis) × the tx's base fee in the including block, it comes from transferable FANG (locks hold it; the burned base fee may come from locked tokens), and txs a multisig's owner key signs, or a validator's consensus key signs for its owner (SF-13), carry none. Admission and execution both check it.
- `valid_until` is the last height at which the tx may execute. Admission and execution require `height ≤ valid_until ≤ height + max_validity` (1 hour of blocks). A tx past `valid_until` can never execute, so wallets may report it as expired.
- **Wire form:** `signing_bytes ‖ public_key (1,952 B) ‖ signature (3,309 B)`. Blocks and mempool gossip carry this form; `Tx::from_bytes` is its strict inverse (no trailing bytes, valid UTF-8, known tags, canonical bools and options). `size()` is its length. JSON stays the API format and rejects unknown fields.
- Addresses: bech32m with the chain's prefix. Statelessly, an address field accepts any known prefix; at admission `from` and every resolved account must use this chain's prefix.

Action tags 0–29 keep their meaning, with two field additions before mainnet: `AddKey` (tag 2) carries the added key's `public_key` and its proof of possession `pop`, an ML-DSA-65 signature over `key_pop_message(chain_id, genesis_hash, account, key_id)` with context `blockula/key-pop/v1`, checked at admission and execution (a key joins an account only with its consent: audit gap-7-2); `CommitVotes` (tag 25) carries `pairs_digest`, the digest of the juror's assigned pairs with each claim's repo and PR, refused if it isn't the seat's (gap-7-6). The digests are BLAKE3 in derive-key mode (`types::action_digest`, `proposal_digest`, `seance_pairs_digest`; `sdk-ts/src/tx.ts` computes the same, checked offline by `sdk-ts/test/tx-vectors.json`). New tags are reserved here so packages never collide:

### 3.2 Blocks (CBlock v2)

```
CBlock { version: u32, parent, height, view: u64, parent_view: u64, timestamp_ms, proposer, exec_height, exec_root, signal: u32, txs: Vec<wire tx> }
```
- Digest domain `BLOCKULA_CBLOCK_V2`.
- `view` and `parent_view` are the simplex round's view and its parent's view (from the consensus context); verifiers require both to match the context. Notarization needs 2f+1 votes, so at least f+1 honest nodes checked them. Executed blocks (`blocks.jsonl`) record them, so missed leader slots are derivable at execution (3.4). Views restart at 1 each epoch; the first block of an epoch has `parent_view = 0`.
- `verify` returns `false` only for permanently invalid blocks (the `Application` contract). Conditions that may still change (we haven't executed the checkpoint or the cited height yet) keep the future pending instead of voting against a valid block.
- `version` is the protocol version in force at `height` (3.9); `signal` is the newest version the proposer's binary supports (upgrade readiness, display only).

### 3.3 State layer

- Store: a Jellyfish-style sparse Merkle tree (BLAKE3; the `jmt` crate or our own) on `redb`, behind a synchronous `StateStore` trait. Commonware's `qmdb` was rejected for now: ALPHA, async-only, and its root commits to operation history rather than the key-value set (`.context/research/commonware.md` §4).
- Every state map is an `imbl::OrdMap` (structural sharing): cloning `State` is O(1), so the API reads a per-block snapshot without the consensus lock and snapshots don't copy the world.
- Every record has a canonical binary encoding and a key `(namespace, bytes)`. The state root is the root of an authenticated tree over `BLAKE3(namespace ‖ key) → BLAKE3(value)`, updated incrementally from the keys a block touched. Inclusion and exclusion proofs are served at `/api/proof/...`.
- Namespaces are `state::ns` (`node/src/state/mod.rs`), never renumbered or reused. Ghost Mode holds 48–63 and staking 64–65. Programs reserve **66–73** (protocol v2, section 7), and 74–79 are held back for them.
- Records, tree nodes and the commit point (height, root, block hash, schema version) are written per block in one transaction to an embedded database, after `blocks.jsonl` and `cblocks.bin` are synced and before consensus is acknowledged. Restart loads the database and re-executes at most the blocks after its commit point: restart time no longer depends on history length.
- The tx index and per-account history live in the database, not in memory.
- Snapshots stream canonical records; a joiner rebuilds the tree and checks the certified root.

### 3.4 Validators, staking and slashing (CV-2, CV-3, CV-4)

- `RegisterValidator` (permissionless, self-bond ≥ `min_self_bond`) creates a candidate that owns a stake pool. Anyone can `Delegate` to a pool; pools account in shares, so rewards compound and slashes scale every delegator alike. Commission is minted to the owner as shares. It's charged at the validator's rate, at most `commission_max_bps`: a lowered cap binds every validator at once, and one above it may step straight down to it (its addresses with it) in one `UpdateValidator`, whose per-epoch step is measured from at most the cap (audit gap-5-1, gap-6-2). Every share pays the same rate, but the owner doesn't get all of it: the part paid on stake of accounts still vesting (other than the owner's own) goes to the treasury, so locked tokens yield no liquid income through a validator their holder picks (3.7, audit xcut-economic-3), and of the part paid on the bootstrap delegation's stake the owner keeps at most `bootstrap_commission_cap_bps` (10%), the rest to the treasury (DEC-5, audit F12).
- At each epoch boundary the next active set is the top `max_validators` candidates by pool stake (not jailed, self-bond ≥ minimum), ties by address, **subject to the churn limit**: newcomers make up at most ⌊(m−1)/3⌋ of the new set of m (a full set replaces at most ⌊(n−1)/3⌋ per epoch), highest stake first. The stake that ranks a pool leaves out the bootstrap delegation's and what accounts still vesting, other than the pool's owner, hold in it (3.7). A set that shrank below four still grows into free seats by one newcomer per epoch on chains without admins (under the churn limit alone a set of one or two could never grow again, with f = 0 for good, and mainnet has no other lever). Past the churn limit (into a set of 2 or 3) that newcomer is needed for every quorum, so it joins only if a quorum of the members it joins (both of two, the one of one) admitted it in the epoch, each by its operator's decision (`AdmitValidator`, `blockula validator admit`; nodes never send it), and its consensus key signaled readiness in the epoch's last tenth (`ValidatorReady`, which writes nothing but that record; candidate nodes send it once admitted), never on stake alone (audit review-fix-staking-2: `staking::admitted`, `showed_up`, counted again at the boundary against the members it carries over). Safety is unchanged; while the set is below four every member, the newcomer too, is needed for a quorum, as they already were, and one the members admitted that then stops voting halts the chain for good (PLAN.md "Known limits"). Votes are equal-weight within the set. `max_validators` (31 at genesis) can be raised by governance to at most 64, the p2p layer's peer-set limit (`consensus::MAX_PEERS_PER_SET`): the active set is the primary peer set and candidates only get the slots it leaves, so the two together never exceed it.
- `Undelegate` sells a number of shares, or (with `shares` 0) the shares `amount` drops buy at the pool's price when it executes, rounded up so at least `amount` unbonds (`staking::shares_worth`; more than the stake is worth is refused). Wallets sign an amount as an amount, so no node's report of the share price decides how much unbonds (audit gap-7-5). Unbonding lasts `unbonding_blocks` (21 days). Unbonding entries stay slashable for infractions committed before they started. A redelegation entry answers for at most what moved: each slash cuts its remainder (what moved, less earlier cuts) and takes that from the delegator's stake in the destination pool, then from that stake's own unbonding, never more. Slashes find a validator's entries through an index by validator and start height, never a scan of every entry.
- **Equivocation:** simplex runs with `track_historical_votes: true` and an `AttributableReporter`-wrapped evidence sink; nodes capture its `ConflictingNotarize`, `ConflictingFinalize` and `NullifyFinalize` reports and submit `ReportEquivocation` with both signed votes. The chain verifies both against that epoch's set and the chain instance's namespace (chain id and genesis hash), from a view no more than `staking::VIEW_SLACK` (1,000) past the highest view a block of that epoch executed in (a key's holder can't make up faults at views consensus never reached), slashes the pool `slash_double_sign_bps` (5%) and the entries that left it since the fault's epoch began, tombstones the validator (never active again), and pays the reporter `reporter_reward_bps` of the slash, at most what the validator's owner lost (so reporting yourself from another account never pays); the rest is burned. **A double-signer is slashed once**, however many faults its key signs: the pool records the height its slash reached back to (`slashed_from`), later evidence from that epoch on is refused, and evidence from an earlier epoch reaches only the entries that left in between. Each drop answers for equivocation at most once, so a leaked key costs a pool one 5% cut, not the whole pool. Punished records are kept as long as their epoch's set, so no `evidence_max_age_epochs` change reopens one.
- Validator sets are kept in state for the whole evidence window (≥ unbonding), not just 8 epochs. Slashing only switches on together with slashing protection (3.9), so a restored disk can't get an honest operator slashed.
- **Downtime:** for a block `(epoch e, view v, parent_view u)`, every view in `u+1 .. v−1` was nullified; charge a missed slot to `leader(e, x)` and credit `leader(e, v)`, where `leader` is `consensus::leader`: simplex's `RoundRobin` elector over the epoch's sorted set, shuffled by the epoch's beacon (SF-1, 3.8), so it names exactly the leaders consensus waited for. Epoch-boundary re-proposals add no height and aren't counted. One block charges each validator at most one missed slot: a stall of many views (lagging verifiers, a partition, a botched upgrade) costs each leader in it one slot, not one per lap of the set. A validator missing more than `downtime_max_missed` of its last `downtime_window` leader slots is jailed (leaves the set at the next boundary, `slash_downtime_bps` = 0.1%) and may `Unjail` after `jail_blocks`, unless that would leave more than f = ⌊(n−1)/3⌋ of the epoch's set jailed or tombstoned: more members than that looking offline at once is a network incident (that many truly offline would have halted the chain), so the rest are charged but not jailed. A change of `downtime_window` or of `downtime_max_missed` starts every ring afresh (each records the pair it was kept under), so a lowered limit judges only the misses after it, never ones the old limit allowed (audit gap-6-4).
- **Pruning:** validators keep a bounded window of consensus blocks and certificates (archive nodes keep all); at full load `cblocks.bin` would otherwise grow ~360 GB/day.
- **Junk blocks (CV-5):** verifiers replay a proposal's unexecuted ancestors with the exact execute path (end-of-block and end-of-epoch steps included), up to 64 ancestors (beyond that they abstain by staying pending), and reject blocks containing unadmittable txs. At execution, every skipped tx costs the proposer `base_fee × size` (from its account, then its self-bond).
- Validator system txs (attestations, beacon, evidence) may name a separate fee payer (the pool owner) so consensus keys only hold a fee float (OPS-1, SF-13). Signed that way they carry no tip: the owner pays the base fee and nothing reaches the proposer (audit F04, F06). What a stolen consensus key can make the owner pay is bounded by the validator's duties (audit F04): such a tx whose action fails isn't admitted (it's never charged; a proposer that includes one pays for it as junk), the key updates the validator for its owner at most once an epoch (and signals readiness or admits a newcomer once an epoch, only while the set is one or two members), and a tombstoned or removed validator's key signs only a reveal for a commitment it made while active. A validator's terms (commission, addresses) and its `Unjail` are its owner's call: the key never changes them from the validator's own account when the owner is another account, so a multisig owner's approvals always apply (audit review-r2-integrate-compose-1).

### 3.5 Governance, treasury, multisig (GOV-1..3, TOK-3, SF-11)

- **No admin keys on mainnet.** Every former admin lever is a proposal kind: `ParamChange`, `TreasurySpend`, `Distribution`, `SetRepo`, `GrantSoul` (bounded), `FlagSybil` (appealed by `UnflagSybil`), `RejectClaim`, `Clawback`, `UnlinkGithub`, `RefundHunt`, `ScheduleUpgrade`, `CancelUpgrade`, `ActivateFeature` (e.g. Ghost Mode), `Text`.
- `Propose` bonds `proposal_deposit` (refunded once the proposal reaches quorum; burned if it doesn't). Voting lasts `voting_blocks` (7 days), then a `timelock_blocks` (2 days) queue, then the action executes at end of block. Upgrades (and cancelling them), feature activations, the parameters that are the token holders' alone (below) and treasury spends above `treasury_large_bps` of the treasury need a ⅔ supermajority; everything else a simple majority. Quorum is `quorum_bps` of unlocked supply.
- `Vote` locks `amount` of the voter's own unlocked holdings (liquid + staked + unbonding) for `conviction` lock periods; weight = amount × conviction multiplier (0.1× with no lock, then 1×–6× for 1–32 lock periods). Locks overlap, constrain transfers out, and are released by `Unlock` after they expire. Unvested tokens can't vote.
- **Bootstrap council.** At genesis almost nothing can vote (insider allocations are locked and locked tokens don't vote; the treasury, community and endowment buckets are keyless). Until `bootstrap_end_height` (12 months), a proposal also passes if ⅔ of the active validator set approves it (`Vote` signed by a validator's consensus key or owner counts as that validator's council vote), provided token-weighted Nay doesn't exceed token-weighted Aye. The timelock still applies. Validators are 22–31 independent operators and the founder holds at most 2 seats, so no single party distributes or spends. The council runs year 1's upgrades, cancellations and feature switches, but a `ParamChange` passes by the council only for the keys in `params::COUNCIL_KEYS` (set size, unbonding, fees, block size, deposits, multisig expiry, names, Ghost Mode limits); every other key, including one added later, is the token holders' alone (`params::tokens_only`).
- **Community distributions** come from the keyless community account through `Distribution { distribution_id, merkle_root, total, claim_until }` proposals (the proposer picks an id no distribution has, at most 1,000 past the next proposal id; it's checked when proposed and when it runs, so proposals landing first can't strand one, a multisig's included; claims close at most 730 days after its proposal's vote ends); recipients `ClaimDistribution` with a Merkle proof (BLAKE3 leaves `(distribution_id, address, amount)`); unclaimed amounts return to the community account after `claim_until`. Criteria are published with the proposal, never before mainnet.
- Issuance parameters can only change within code bounds (floor ≥ 0.5%, stakers' share ≥ 50%) and with a ⅔ token supermajority.
- Governance's own safety parameters (voting and lock periods, the timelock, quorum, the supermajority, the large-spend line, the spend gate, the council's end) and the validators' own economics (issuance, `tip_cap_multiple`, the commission bounds, the bootstrap delegation's commission cap, the self-bond and insider-delegation cap, slashing, jail, downtime, the evidence window, the reporter's share, beacon-miss slashes: `params::VALIDATOR_KEYS`) change only by the ⅔ token supermajority, never by the bootstrap council, which is the validators (it can't extend itself, open spending early, weaken the vote that checks it, pay itself more or soften its own penalties; audit F15, F16, F01, review-integrate-merges-1). The safety parameters also stay inside bands in code, with ceilings as well as floors (the supermajority 60–80%, quorum 1–10% and 5M–50M FANG, the spend gate at most a year past the vote that moves it), so no vote can lock the next one out (review-fix-gov-3; GOVERNANCE.md "Safety parameters"). The evidence window has a floor of two weeks (`params::EVIDENCE_WINDOW_FLOOR_DAYS`), and unbonding can't be shorter than the window, so the weak-subjectivity period joiners rely on never falls below a week (audit gap-6-1).
- `ActivateFeature` (security-critical switches such as Ghost Mode) also needs the ⅔ supermajority; `DeactivateFeature` takes a simple majority, so switching a feature off is never harder than switching it on.
- The treasury is a keyless system account; only `TreasurySpend` moves funds out. Quorum has an absolute floor (`quorum_floor`, in FANG) as well as `quorum_bps`, and spending proposals are rejected before `governance_spend_height` (≈ 6 months), because almost nothing can vote at launch.
- `MultisigCreate` turns an account into an M-of-N multisig of its owner keys: owner-only actions then need `MultisigPropose` plus approvals; session keys keep working within their limits.
- Hunts: only the creator awards. Governance can refund a hunt's funders; nobody can redirect escrow.
- Soul: bootstrapped by a published `soul_ledger` in genesis; after that only juries and bounded `GrantSoul` proposals change it.
- The full rules (tally, council, deposits, the distribution Merkle format and its SDK helper, multisig) are in [GOVERNANCE.md](GOVERNANCE.md).

### 3.6 Fees and issuance (TOK-1, TOK-2)

- **Base fee per byte** for block `h` is fixed when block `h − 17` executes (`MAX_EXEC_LAG + 1`), so every proposer within the lag limit knows it exactly. Target fullness 50% of `MAX_BLOCK_BYTES`, max change 12.5% per block, floor = today's `min_fee` formula. The base part is burned.
  - *As built (P-ECON, `econ.rs`):* the state keeps the fee slot (flat part, rate in milli-drops per byte, `max_block_bytes`) of the last executed height and the 17 after it; parameter changes reach slots 17 blocks later. A proposer more than 17 blocks ahead of its state proposes no txs; a block with txs must cite `exec_height ≥ height − 17`, so a verifier checks its size and every tx's fee exactly once it has executed that height. Statelessly a fee is only checked against the lowest base fee any parameters allow.
- Proposals order mempool txs by tip per byte; the mempool evicts the lowest tip per byte when full. Tips are capped at `tip_cap_multiple` × the base fee (3.1).
- Validator duties (beacon commits and reveals, equivocation evidence, claim and revert attestations, signed by an active validator's consensus key; a reveal also by a validator that left the set but still owes it) carry no tip, so the mempool keeps them in a lane of their own: at most 2 per validator and kind of duty, outside the 5,000-tx limit, never evicted for a tip, and first in proposals (audit F32/F56). The lane is a prefix of each sender's queue: a duty behind its account's other txs queues like them until they're gone, so it can't shield them from eviction or wait behind them in proposals (review of F32). Mempool policy only; block validity doesn't change.
- **Issuance** is minted at each epoch boundary: `supply × rate_ppm(year) / epochs_per_year`, with the rate starting at 6% and decaying 15% a year to a 1.5% floor (integer ppm math). Split 70% to active validators' pools (pro rata to stake, none for jailed or tombstoned validators), 20% to the contribution pool, 10% to the treasury.
- Account creation burns `account_creation_fee` (0.1 FANG at genesis).

### 3.7 Allocations, vesting and locks (TOK-4, OPS-2)

- Staking rewards earned by locked tokens are locked on the same curve (otherwise a vesting allocation yields liquid income before its cliff). An account with vesting locks can delegate at most `insider_delegation_cap` (1% of supply) to any one pool.
  - *As built:* a still-vesting account's stake counts at cost (its principal) toward covering its lock and toward what it may vote with: gains not sold yet neither free locked tokens nor vote before they vest (`econ::free`, `econ::voting_balance`; audit F03, xcut-economic-1), and sold, they join the lock. The commission its stake pays in a pool it doesn't own goes to the treasury, not to the pool's owner, so a 100%-commission validator (an accomplice's, or the insider's own other account) can't turn locked stake into liquid income (audit xcut-economic-3).
  - *Insider seats (audit xcut-economic-2), enforced by the chain at every boundary:* locked stake ranks only its holder's own pools (an insider's delegation to someone else's pool earns but doesn't count toward that pool's rank); a newcomer owned by an account with unvested tokens joins only if that account then holds no other seat (its locked tokens fund one validator that ranks, not one per 1% of the supply); and validators owned by the founder's accounts (`bootstrap_excluded`) take seats only while they hold at most 2 (DEC-3) and fewer than f = ⌊(m−1)/3⌋ of the set of m, so insiders can't halt the set or veto its council, even with one more member down. The per-pool cap stays. Seats already held (genesis seats) aren't taken away; the rules hold newcomers to them.
- Accounts carry `locks: [Lock { id, amount(curve), reason }]`. A vesting lock is a curve (`start`, `cliff`, `end`, `total`): the locked amount at height `h` is the unvested part. Transferable balance = liquid − max(0, max_lock − staked − unbonding). Locked tokens can be staked and delegated, never transferred.
  - *As built (P-ECON):* after every tx's action, each account it touched must hold transferable ≥ 0 (the sender: no less than it had, since the burned base fee may be paid from locked tokens; the tip may not, 3.1), so every module's escrows and payments respect locks without checking them. The treasury's 4-year unlock and the endowment's 10-year stream are vesting locks on those keyless accounts; each epoch the endowment's vested part moves into the contribution pool.
- `blockula genesis build --spec <spec.toml>` produces a byte-identical `genesis.json` and its hash from reviewed inputs (allocations with vesting, operators with their own keys and proofs of possession, parameters, reserved names, Soul ledger, `faucet: false`, `validator_admins: []` for mainnet). Several parties must reproduce the hash.

### 3.8 Randomness beacon and Proof of Contribution (CRY-3, GOV-3)

- Each active validator commits `BLAKE3(chain_id, e + 2, validator, secret)` for epoch `e + 2` during epoch `e` and reveals during `e + 1`. The beacon for `e + 2` is `BLAKE3` of the previous beacon, the epoch and the reveals sorted by validator (with none, of the previous beacon and the epoch: a hash chain). Validators that commit but don't reveal are jailed and slashed `beacon_miss_slash_bps` (times one more for each miss in the kept values, at most the parameter's ceiling); the beacon step runs first at the epoch boundary, before issuance and set selection, so the withholder earns nothing for that epoch and isn't in the set for the epoch it biased, and a jailed validator can't commit. Epoch 0's value comes from genesis. The one remaining lever is withholding a reveal (one bit per validator, paid for with that; PLAN.md "Known limits" bounds what a bit is worth).
- Séances open only at the last block of every n-th epoch (n = the epochs a Séance spans), seeded from that epoch's beacon and the Séance id, over jurors who joined and claims whose revert window ended before the previous epoch began (so before anyone could know the value), and vouch conflicts as of that cutoff (a vouch withdrawn after it still counts); jurors are ranked individually by the seed, and pair only different people's claims. The opening block's proposer has no influence. Each epoch's leader order is `RoundRobin` shuffled by a seed from its beacon (SF-1); downtime accounting elects leaders the same way (`consensus::leader`).
- Validators re-check verified claims for reverts during their revert window (`claim_maturity_blocks` after verification) and attest the revert commit (`AttestRevert`); a quorum of the current set on the same commit rejects the claim and claws back its rewards. Admin rejection is gone.

### 3.9 Upgrades and halts (OPS-3, OPS-5, OPS-6)

- State holds an upgrade schedule `[(version, activation_height)]`, changed only by `ScheduleUpgrade` proposals (which append) and `CancelUpgrade` proposals (a ⅔ supermajority with no timelock, which withdraw an entry and those after it; audit F50; the withdrawn version numbers, and those of the upgrade proposals it supersedes that passed (before it ran or after), are never scheduled again, since halts and readiness compare only numbers, and a cancellation supersedes every `ScheduleUpgrade` proposed before it ran, a multisig's stored one included, keeping the highest superseded number so the next upgrade is advised past it; every vote of a block closes before anything runs in it, so which proposals passed doesn't depend on ids; review-fix-ops-1, -2, review-r3-gov-1, -2); a version is at most `MAX_VERSION_STEP` (16) past the newest ever scheduled, withdrawn or superseded, so the advised number is always schedulable (review-r2-gov-1, review-r3-gov-1); an upgrade activates at least `MIN_UPGRADE_LEAD` (64) blocks after the block that schedules it and at most 365 days after its proposal's vote ends (the same bound when proposed and when it runs; review-r3-gov-3), and is withdrawn at least 64 blocks before it would activate, so a verifier that has executed within 64 blocks of a height knows its version (and waits until then). `upgrade::version_at(h)` gates behavior. A node whose binary doesn't support the version scheduled at the next height halts cleanly before executing it instead of diverging: it doesn't vote on or propose later blocks; validators exit (code 11), full nodes keep serving reads and `/api/health` says why.
- `--halt-height H` stops after executing `H` (coordinated restarts, incidents): no votes or proposals above `H`, exit code 10 on validators.
- **Slashing protection that survives restores:** besides a last-signed-view record checked before each signature, a validator that starts up only signs views later than the newest view it observes from the network for its epoch (a few views of abstention per restart), and halts if it sees a vote under its own key that it didn't produce in this run. A restored volume therefore can't double-sign even though its record rolled back with it. Only certificates (quorum proofs) count as observations, so no single peer can silence a validator; if the network makes no progress without it (a full restart), it signs again after ~20 s on its record alone (`protection.rs`), but only once its HTTP peers show the network standing still where it is (more of those that answer at exactly its height than claim more, its height not moving for most of those ~20 s), with no verified sign of a later block (certified blocks a peer proves, its own certificates) and no later-epoch traffic from more of its epoch's validators than can be faulty, and only above the newest block it executed. Silence alone (a node cut off, or stuck in an epoch the network has left) keeps it abstaining: the escape fails safe (audit F18). No single unverified source can keep a restarting network from escaping (review of F18), and `--network-halted-at H`, the operator's word, overrides unverified answers.
- On-disk formats carry a schema version and migrations.

### 3.10 Sync trust (CRY-2)

- Releases embed checkpoints (height, block hash, validator-set hash) for known chain ids, and the mainnet genesis hash. `join` requires `--genesis-hash` or a known chain id, and refuses snapshots that contradict an embedded checkpoint.
- The fast-sync manifest carries a certificate for the epoch anchor (the boundary block before the current epoch), so nothing in it is taken from the peer on trust.
- The weak-subjectivity period is documented and shorter than unbonding. It follows governance: a node enforces the shortest of the genesis parameters' period, the one its release recorded, the one its own executed state's parameters set, and, before it syncs, the shortest its peers report in `/api/status` (they can only shorten it, and a peer's report never below the protocol's floor of a week: half the evidence window's floor of two weeks).
- Handoff signatures bind the chain instance like votes and certificates: `BLOCKULA_HANDOFF_V3` signs the genesis hash, the chain id, the epoch and both sets' hashes, so no other genesis under the same id accepts them.

## 6. Ghost Mode

Recommendation (b) from `.context/research/ghost-mode.md`: build it, ship it **disabled**, and turn it on with `ActivateFeature { ghost }` only after a dedicated ZK audit, a clean under-constraint sweep and fuzzing, a cryptanalyst's sign-off on Poseidon2, ≥ 4 weeks on testnet with a bounty, and counsel. A shielded-pool soundness bug is a silent infinite mint (Zcash 2018; Orchard CVE-2026-54496 in May 2026).
- One Plonky3 (`=0.8.0`) action circuit on KoalaBear with hiding FRI: 2 spends, 2 outputs, dummies allowed, Poseidon2 commitments, position-bound nullifiers, value balance with carried u64 limbs.
- State: commitment tree frontier and a window of recent roots, the nullifier set, the transparent pool balance (a turnstile: unshield can never exceed it, and it's in `check_invariants`), a governance pool cap, and the feature record.
- Tags: 50 `Shield`, 51 `PrivateTransfer`, 52 `Unshield` (unsigned: the proof authorizes them, nullifiers prevent replay), 53 `SetGhostAddress` (1,216-byte ML-KEM address published under a `.boo` name), 54 `GhostPause` (takes effect once f+1 validators sign; f+1 can halt the chain anyway, so it adds no power), 55–59 reserved.
- Size limits per tag: ghost txs up to 256 KiB, at most 1 MiB of ghost txs per block.
- Notes: ML-KEM-768 (`ml-kem =0.3.2`) + XChaCha20-Poly1305; incoming, full and outgoing viewing keys. Session keys can't spend shielded funds. Every hash use is versioned so a later pool can migrate.
- Full design: `docs/GHOST-MODE.md`.

## 7. Programs (protocol v2)

Third-party programs are protocol v2. [PROGRAMS.md](PROGRAMS.md) specifies them and [PROGRAMS-PLAN.md](PROGRAMS-PLAN.md) plans the work; on programs, PROGRAMS.md wins over this file. In short:
- WebAssembly run by a fuel-metered interpreter in its own crate (`node/vm`; soroban-wasmi 29.x by default, the exact pin chosen in phase 0), written in Rust, and added as one more protocol module (`programs`, shaped like `ghost`).
- Tags 62–70 (3.1) and namespaces 66–73 (3.3), with 74–79 held back. The state schema moves from 9 to 10 at activation. Compute is a second base-fee dimension (fuel) charged on the declared limit, and storage takes refundable deposits.
- Every program behavior is a function of the protocol version in force (3.9), so a v2 binary computes v1's state exactly below the activation height (PROGRAMS.md 14.4). P7 (PROGRAMS-PLAN.md) plumbed the version into every execution path first, and only a dev or test chain a binary summons may schedule v2 from its genesis (`upgrades`; neither `blockula genesis build` nor mainnet's genesis can), which only such a chain's nodes run until the release that ships it (`upgrade::supported_version`).
- Behind the `programs` feature: `ActivateFeature { programs }` takes the ⅔ supermajority, which the council may give in year 1 (3.5). The training wheels: a 10M FANG cap on what programs hold, an f+1 validator pause that lapses after 3 days, exit-only while the feature is off, and a tokens-only freeze that lapses after 30 days.
- Live on mainnet as soon as they're ready: formats frozen, the audit closed and at least 8 weeks on testnet-2. On at genesis if that comes first, otherwise the council activates them. They're reviewed by AI agents (Claude with Fable), not externally audited.
