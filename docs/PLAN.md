# Blockula plan

## Decisions (locked)

| Decision | Choice |
|---|---|
| Name / token | Blockula / FANG (1 FANG = 10⁹ drops) |
| Names | `.boo`, native to the protocol |
| Node | Rust; multi-validator consensus on **Commonware** primitives (Phase 1) |
| Execution | **Native modules only** in v1 (accounts, transfers, names, shielded pool, storage, staking). WASM/RISC-V contracts in v2. No EVM (it's bound to ECDSA). |
| L1 vs L2 | Standalone L1, because settling on Ethereum would bring back its ECDSA/BLS weakness |

## Why this is quantum-safe

- **Signatures:** ML-DSA-65 (FIPS 204) for users and validators. SLH-DSA (FIPS 205, hash-only) for cold recovery keys.
- **Hashes:** BLAKE3-256. Grover's algorithm only halves security, and 256-bit addresses keep ~128-bit collision resistance even against quantum attacks.
- **Encryption:** ML-KEM-768 (FIPS 203) for note encryption and The Crypt.
- **Network:** validators authenticate with ML-DSA-65 and derive p2p session keys from hybrid X25519 + ML-KEM-768, so recorded traffic stays private unless both break. The node's outbound HTTPS prefers `X25519MLKEM768`. Details: [PQ-TRANSPORT.md](PQ-TRANSPORT.md).
- **ZK:** hash-based STARKs (FRI + Poseidon2, e.g. Plonky3) only. No Groth16/KZG, because pairings fall to Shor's algorithm.
- **Passkeys:** WebAuthn signs with P-256, which is not quantum-safe, so the passkey never signs on-chain. Its **PRF extension** output (symmetric) derives the ML-DSA key: `seed = BLAKE3-KDF("blockula passkey wallet v1", prf)`. Implemented in `sdk-ts/src/passkey.ts`.

## Accounts

Native account abstraction (Phase 1). Each account holds a list of authorized keys with roles:
- **device:** passkey-derived ML-DSA keys (one per passkey provider)
- **recovery:** SLH-DSA cold key (downloadable recovery kit) and/or guardians (social recovery)
- **agent session:** ML-DSA key with spend limit per day, expiry and allowed modules. Replaces today's client-side `BLOCKULA_MAX_SEND`.
- **Fallback:** for authenticators without PRF, a password-encrypted key, clearly labeled as weaker.

## 👻 Ghost Mode (private transfers) and 🪦 The Crypt (private storage), Phase 2

- An Orchard-style shielded pool: notes are Poseidon2 commitments, spending publishes a nullifier, and a STARK proves validity. Note contents are encrypted to the recipient with ML-KEM.
- **Viewing keys** for selective disclosure (accountants, auditors, compliance).
- Proofs are about 50–200 KB, so validators **recursively aggregate** a block's proofs into one.
- The explorer shows "👻 a ghost transaction happened" (nullifier, fee, proof size), never parties or amounts. The tutorial walks users through exactly this.
- **The Crypt:** blobs are ML-KEM-encrypted and stored by nodes. On-chain: commitment + access list + storage deposit. Sharing re-encrypts the data key to another user.
- Later: private names, private voting, selective-disclosure credentials ("over 18" without revealing a birthday).

## Tokenomics (FANG)

- **Fees:** the per-byte base fee is **burned** 🔥; tips go to the proposer. Priced by bytes because post-quantum signatures are about 3.3 KB. Protocol v1: it moves with block fullness (12.5% a block at most, never below the old minimum) and is fixed 17 blocks ahead (MAINNET-DESIGN 3.6).
- **Issuance:** starts at 6% a year, decays 15% a year to a permanent **1.5% tail emission** so security never depends on fees alone, minted every epoch. Split 70% stakers / 20% contribution pool / 10% treasury (see Proof of Contribution and [TOKENOMICS.md](TOKENOMICS.md)).
- **Names:** length-based price (3 chars: 100, 4 chars: 25, 5+ chars: 5 FANG) to the treasury, for a year; renewal costs 20% of the price a year, with a 30-day grace, so squatters bleed (protocol v1, DEC-11). A name keeps the grace it was registered or last renewed with: governance lowering `name_grace_blocks` shortens only later names' graces (raising it lengthens every grace).
- **State growth:** opening an account burns 0.1 FANG and names renew yearly; every other record is bonded (DEC-6).
- **Treasury:** 10% of issuance plus name fees. Pays for sponsored onboarding txs (new users need zero FANG), faucets, audits and grants.
- **Ghost Mode:** a small verification premium, partly offset by aggregation.
- **Health targets:** ≥50% staked, Nakamoto coefficient ≥10, slashing for double-signing (heavy) and downtime (light).
- Get legal review before any sale or distribution.

## 🪦 Proof of Contribution (rewarding useful work)

**Principle:** anything counted automatically gets farmed (commit counts, lines changed, even merged PRs). So rewards come from **people with something at stake**, are paid from a **fixed per-epoch pool** (spam dilutes other contributors instead of printing tokens), and **vest slowly** so they can be clawed back. This is separate from consensus: block production stays pure proof-of-stake, because mixing in reputation would give attackers a cheaper path to control.

### Pieces
- **Souls:** non-transferable reputation. Earned slowly, decays over time, can't be bought. It boosts reward share, jury eligibility and voting weight.
- **Identity:** link GitHub by posting your key id in a public gist; validators check it independently. New identities need a **vouch** from someone with Soul. Vouchers earn a small cut of the newcomer's early rewards, and lose stake and Soul if the newcomer turns out to be a sybil.
- **Repos:** registered with a stake plus a governance vote. Blockula's own repo is #1, so building Blockula earns FANG.
- **Claims:** "PR #123, merge SHA, my GitHub id" plus a small refundable bond. Validators each check the GitHub API, and a claim needs most of them (e.g. 2/3) to agree. A PR pays only after **30 days without a revert**.
- **Séances (review juries):** on a fixed epoch cadence, a random jury of staked reviewers is drawn. The randomness comes from a commit-reveal beacon among the validators (hash-based, so quantum-safe). Jurors **commit, then reveal** pairwise judgments ("which PR mattered more?"). Jurors who keep diverging badly from consensus lose Soul. Reviewing is itself rewarded work.
- **Payout:** governance splits the pool across repos; maintainer weights and jury scores split each repo's share across PRs. Within a Séance, a person's claims are **rated together** (one win rate over all their comparisons) and count **one after another, each a quarter of the one before** (all of them together less than 4/3 of one claim at that rate), so 50 tiny PRs earn less than one solid PR. Rewards **vest over 90 days with clawback**.
- **Hunts:** bounties on specific issues, funded by anyone. Explicit demand, and the least gameable reward type, so they ship first.
- **Covens:** teams claiming Hunts together, with the payout split recorded on-chain and shared streaks. **Seasons** (Season 1: October) with leaderboards ranked by Soul, not tokens.
- **Profiles** in the explorer: merged PRs, Soul, who vouched for whom.

### Status: Hunts v0 and Proof of Contribution v1 are live on the testnet
**Hunts**
- `create_hunt` escrows a bounty on a GitHub issue (min 10 FANG, ≤ ~1 year). `fund_hunt` lets anyone add to it. `award_hunt` (the creator only) pays it out once and records the PR; self-awards are allowed but flagged. `cancel_hunt` (creator after expiry; an admin any time on dev and test chains; a `RefundHunt` proposal on mainnet) refunds every funder exactly what they put in.
- `blockula hunt award <id> --pr <n>` checks on GitHub that the PR merged into the hunt's repo's default branch, looks up the account its author linked, confirms, and signs the award (`--to` names a recipient instead, `--familiar` credits their agent). `hunt list|show|create|fund|cancel` cover the rest.
- `link_github` is an on-chain claim: one handle per account, one account per handle. The holder or an admin (a governance `UnlinkGithub` proposal on mainnet) can unlink. A proposal holds the handle for its proposer for one voting period, so only the account that asked can link it then and a squatter can't link it again the next block; and a handle with a verified claim (validators checked its gist) can only be linked by the account its claims are credited to. Nodes check it off-chain: a public gist owned by the handle must contain the account's address (`/api/github/{handle}`). Validators re-check it for every contribution claim.
- `register_familiar` marks a session key as an agent Familiar. Awards can credit it, and profiles show "won by vlad.boo's Familiar 'claude'".

**Proof of Contribution v1** (`node/src/poc.rs`; explorer Contribute page; `blockula contrib …`; SDK; MCP `contribution_pool`, `submit_contribution`, `my_contributions`)
- **Souls:** milli-Soul per account, never transferable. It decays (half-life ~1 year, integer math) and is earned only from jury outcomes: up to 10 Soul for an accepted claim (scaled by its claimant's rate in the Séance, each after their first a quarter of the one before), +1 for a juror who agrees with the outcome. It's lost for spam claims (−20), diverging badly as a juror (−2), not revealing (−2, so holding back a bad ballot never pays), or vouching for a sybil (−50). Season 0 admins bootstrap it with `grant_soul` (≤ 100 per grant); governance replaces that in Phase 3. Soul gates vouching (10) and jury duty (5), raises the open-claim cap (3 + 1 per 10 Soul, max 20) and boosts payouts up to 1.5× (at 100 Soul).
- **Vouching:** `vouch` bonds 10 FANG on a newcomer: someone with no Soul and no judged work (one vouch per 10 Soul held, max 10). It's locked for ~90 days, then `unvouch` returns the bond; the newcomer can decline it any time. Declining doesn't get the voucher off the hook: until the lock would have ended, and while a `FlagSybil` proposal names the newcomer, the bond stays held and the slot taken, and a sybil flag costs the voucher the bond and 50 Soul as if the vouch were live; a voucher withdrawing after the lock while such a proposal is open waits too. Held bonds come back at the first epoch boundary after that. The vouch keeps the two off each other's juries, and a Séance's draw is public an epoch before it opens, so a vouch withdrawn at or after a Séance's cutoff still counts for that Séance: dropping it once the seed is public neither seats a juror on a claim it mustn't judge nor moves anyone's seat. While the vouch is young, the voucher gets 10% of the newcomer's rewards. `flag_sybil` (Season 0 admins) zeroes the account's Soul, rejects its open claims, claws back its unvested rewards and its vouchers' cuts of them, removes it from the jury pool, voids its vouches, and slashes its voucher's bond and 50 Soul. The appeal is a governance proposal, `UnflagSybil`: it lifts the flag (the account, and its GitHub handle, can earn again) but restores nothing the flag took.
- **Repos:** `set_repo` (admins) puts a repo in the pool with a weight of 1–100. Removing one refunds the claims still waiting on it.
- **Claims:** `submit_claim(repo, pr)` needs a linked GitHub handle and Soul or a vouch, and bonds 1 FANG × (1 + open claims). A registered Familiar session key may sign it for its sponsor; the bond counts against its spend limit. One claim per PR.
- **Validator-attested GitHub facts:** every validator's node checks pending claims (the PR is merged into that repo's default branch, authored by the claimant's handle, and the handle's gist contains the claimant's address) and signs `attest_claim` with what it found. A BFT quorum (n − ⌊(n−1)/3⌋) agreeing on the merge commit verifies the claim; a quorum refuting it rejects it (bond to the pool; the PR can be claimed again). The first verified claim locks the GitHub handle to that account: relinking the handle elsewhere can't split one person's work across accounts. Open PRs are re-checked later, and claims never settled within ~7 days are refunded.
- **Revert window:** a verified claim waits ~30 days before it can be judged. Meanwhile every validator's node re-checks its PR on GitHub and signs `attest_revert` with the revert commit. A revert must say so in so many words (a commit with a line starting `This reverts commit <merge sha>`, or a merged PR's description with that or GitHub's `Reverts owner/repo#N`; a mention of the PR anywhere else doesn't count, and a commit message saying `Reverts #N` doesn't either, since the PR's own commits could) and its diff must undo the PR's: more than half the lines the PR added and removed, removed and added back, and more than half of its files with no lines to compare (binary files, diffs too large for GitHub to show) whose pre-PR state is known brought back to it (a PR with both needs both); nothing is attested without that check; a BFT quorum of the current set naming the same commit rejects the claim (bond to the pool, `node/src/beacon.rs`). After the window a revert no longer counts. `reject_claim` (admins on test chains, a governance proposal on mainnet) handles the rest and claws back a scored claim's rewards (the voucher's cut too) and Soul. Rejecting a claim that was never verified frees the PR for its real author.
- **Randomness beacon** (`node/src/beacon.rs`): during epoch e every active validator commits to a fresh secret for epoch e + 2 (BLAKE3 over the chain, epoch, validator and secret), in the second half of e + 1 it reveals it, and at the end of e + 1 the value for e + 2 is BLAKE3 over the previous value, the epoch and the sorted reveals. Committing without revealing gets the validator jailed and slashed `beacon_miss_slash_bps`. Secrets are written to `beacon-secrets.json` (0600) under the validator's home before the commitment is sent, so restarts don't lose them. The value also shuffles each epoch's leader order.
- **Séances:** they open only at the last block of every n-th epoch, where n is the number of epochs a Séance spans (weekly on mainnet), if no Séance is open and claims of ≥ 2 people and ≥ 3 jurors are eligible (claims oldest first, ≤ 64). Eligible means fixed before the opening epoch's beacon could be known: jurors who joined the `join_jury` pool (5 Soul, 10 FANG bond, owner keys only, so no Familiars) and claims whose revert window ended before the start of the previous epoch. The seed is BLAKE3 of the opening epoch's beacon and the Séance id; each eligible juror gets its own rank from it and the 7 best-ranked sit, so nobody can steer the draw by reordering or censoring the opening block, or by joining or leaving. Each juror gets up to 24 random pairs of two different people's claims (one person's claims are never compared with each other), never involving their own claims or anyone they vouched for (or who vouched for them). A Séance needs claims of at least 2 people; a person alone with their claims waits for company. For the first ⅔ of the Séance (~7 days in total) jurors `commit_votes` BLAKE3(id, juror, votes, spam flags, salt); in the last ⅓ they `reveal_votes`. Votes are `a`, `b` or `=` per pair, plus claims they flag as spam.
- **Scoring:** fewer than 3 reveals and nothing is decided: claims carry over, the budget goes back, and no-shows still pay. Otherwise a claim's score is its win rate across revealed comparisons (a tie counts half), and a person's rate is their win rate across the comparisons of all their claims in the Séance that weren't marked spam. Flagged by ≥ 3 jurors and by more than half of those who saw it: spam (bond to the pool, −20 Soul). A claim fewer than 3 jurors saw can't be marked spam (it's scored, never slashed on so few views), and a flag on a claim enough jurors saw that the jury didn't uphold counts against the flagger's agreement. A claim below 15%, or whose claimant's rate is below 15%: bond back, no reward. No comparisons at all: carried over to the next Séance. Jurors are graded against the outcome: ≥ 60% agreement earns Soul and a share of the jurors' budget, < 40% loses Soul, and voting `=` on everything (50%) earns nothing. No-shows lose 10% of their bond and 2 Soul, and are benched. Jurors flagged as sybils mid-Séance don't count.
- **Payout:** each Séance reserves up to 25% of the pool's balance when it opens, scaled by the number of people whose claims it judges (the full share from 16; one person's many claims count once), so a tiny Séance can't drain the pool and volume doesn't grow it. Jurors get 10% (by agreement); claims get the rest. Per person (the claimant account: every handle it linked counts together, and a sponsor's Familiars count as the sponsor), a weight is Σⱼ (repo weight × rate)ⱼ / 4ʲ × Soul boost (up to 1.5×). A claim's rate is the person's win rate pooled over every comparison of their claims in the Séance (every claim the jury judged and didn't mark spam, those below the threshold too), capped at the claim's own win rate: the pooled rate is a ceiling, never a lift, so a weak claim in a heavy repo isn't paid at the rate the person's strong claims in a light repo earned (audit review-r4-poc-2). The index j = 0, 1, … ranks their accepted claims heaviest repo first (then by score): the first counts in full and each further one a quarter of the one before, so all of them together count less than 4/3 of one claim at the person's rate (`CLAIM_RANK_SHIFT`; audit xcut-economic-opus-1). A claim's Soul (10 × its rate) is ranked the same way, by score. The rate is pooled, never the best claim's: each claim's own win rate comes from a handful of comparisons, so the best of k claims of one quality scores higher the more there are, while a pooled rate only gets steadier (paying the best claim, 16 weak PRs out-earned a solid one in 40 of 40 simulated Séances with honest jurors who pick a side between two weak PRs). So in expectation k claims of one quality earn at most 4/3 of what one does, and a pile of claims each judged worse than someone's solid PR and no better than the rest rates under half of it: even with the full Soul boost against a newcomer's (4/3 × ½ × 1.5 = 1) it stays below, on average, in FANG and in Soul (a draw that happens to rate the pile above half overall can edge past it: 3 of 40 simulated Séances at 16 claims). A claim's payout is its ranked weight's share of its person's. Rewards are grants that vest linearly over ~90 days: `withdraw_vested` pulls what has vested, `clawback` (admins) returns the rest to the pool. Rounding dust and unused budget go back to the pool.
- **The pool** is a system account (`🪦 contribution pool`) funded by `fund_pool`, plain transfers to it, every slashed bond, 20% of each epoch's issuance and the endowment's vested stream (`econ::issue`).
- Timings come from genesis (`contribution`) or default to the durations above. `blockula dev` uses minutes instead (90-block Séances, no maturity wait; 60-block epochs, and staking and governance periods of a minute or two, docs/GOVERNANCE.md) so the whole loop can be tried locally, and `summon` takes `--seance-blocks`, `--claim-maturity-blocks` and `--vesting-blocks`.
- API: `/api/contributions`, `/api/claims`, `/api/claim/{id}`, `/api/seance/{id}` (each juror's assigned pairs), `/api/souls`, plus a `contribution` section on `/api/account`.

### 🐈‍⬛ Familiars: agent contributions, encouraged
Agents are first-class contributors, but every agent is the **Familiar of a human sponsor** who has Soul.
- **Binding:** a Familiar is a session key on the sponsor's account plus an on-chain `familiar_of` link. Its rewards go to the sponsor (who can set a split), and its mistakes cost the sponsor's Soul.
- **Volume barely pays:** all of a sponsor's Familiars are pooled as one person, their claims rated and ranked together (one win rate; the first in full, each next a quarter: in expectation at most 4/3 of one claim of the same quality). There's a per-Soul-tier cap on Familiars and open claims, and the claim bond grows with the number of open claims.
- **Agent-shaped work pays best, because it can be checked objectively:**
  - Hunts with **acceptance tests**: the bounty pays when validators re-run the declared tests and they pass.
  - **Fuzzing and bug repros**: a crash that reproduces deterministically from the submitted input.
  - **Benchmarks**: validators re-run them to measure the gain.
  - **Test coverage**, docs, translations and spec conformance.
- **Network work:** Familiars can run nodes and validators through `start_dev_node` and `blockula join`. Validator rewards come from stake and uptime, so they can't be farmed.
- **Triage:** Familiars can pre-screen claims and flag spam. They earn only when a human jury upholds the flag; jurors themselves must be human.
- **MCP tools** (Phase 1.5): `list_hunts`, `claim_hunt`, `submit_contribution`, `my_contributions`, `become_familiar`. AGENTS.md gets a "contribute to Blockula" prompt: *find an open Hunt, implement it, make its acceptance tests pass, submit.*

### Why farming fails
| Attack | Defense |
|---|---|
| Bot or AI spam PRs | Must be merged and survive 30 days, bond slashed if the jury marks spam, a sponsor's claims in a Séance rated together (one pooled win rate; each after the first counts a quarter of the one before) |
| Fake GitHub accounts (sybils) | Vouch required, voucher slashed if the account is fake, rewards start small until Soul builds up |
| Maintainer merging their own fake accounts' PRs | Juries randomly audit each repo, repo budget slashed if caught, vesting with clawback |
| Jurors colluding | Random selection, commit-reveal, no reviewing people you vouched for, flagging of suspicious reviewer–author pairs |
| Typo and whitespace PRs | Minimum score threshold |
| Fleets of agents | Pooled per sponsor, capped by Soul tier, sponsor slashed for spam |

### Forks and governance
- **Code forks:** a share (e.g. 10%) of a fork's rewards flows back to the original repo's contributors.
- **Chain forks:** `blockula summon` can start from a Soul-ledger snapshot, so a forked network keeps its community. Forking stays a credible exit.
- **Voting weight:** about √stake + Soul. **Conviction voting** for treasury and repo budgets. Protocol upgrades: validators signal readiness in the blocks they propose, then a vote and a timelock schedule the activation height, and another vote can withdraw it until 64 blocks before (OPERATIONS.md "Upgrades"). **Private ballots** via Ghost Mode later (tallies public, votes hidden).
- **Issuance split:** 70% stakers / 20% contribution pool / 10% treasury. The pool is fixed per epoch, so contribution rewards never add inflation.

## Network and sync

What runs today (Commonware `=2026.9.0`: consensus, p2p, broadcast, storage, runtime):
- **Consensus:** simplex BFT. Votes and finality certificates are ML-DSA-65 (deterministic FIPS 204 signing, the Commonware namespace is the FIPS 204 context string; `node/src/pq.rs`). A certificate is a signer bitmap plus one 3,309-byte signature per signer, with no aggregation. Leaders rotate round-robin; `block_time_ms` paces proposals.
- **Deferred execution:** consensus orders blocks (parent, height, proposer = leader, timestamp, txs as signed JSON, plus the proposer's latest executed `(height, state root)`). Before voting, validators check structure, size limits (512 txs / 4 MiB), timestamps, proposer, tx signatures, chain id and minimum fee, and the attached state root if they've executed that height. Finalized blocks are executed in order: invalid txs are skipped, and `blocks.jsonl` is synced before marshal is acknowledged.
- **Dissemination and backfill:** marshal (standard/inline) broadcasts full blocks, delivers finalized blocks in order, and backfills anything a restarted validator missed.
- **p2p:** `authenticated::discovery` over tokio with ML-DSA-65 identities (the validator's account seed). The genesis lists every genesis validator's `public_key`, `p2p_addr` and `http_addr`.
  - `--bind` sets the local interface (127.0.0.1 by default; 0.0.0.0 or :: on servers). Peers dial the advertised address, which comes from genesis or from a registration.
  - The `recommended` preset is used for public advertised addresses and `local` for private ones.
- **Epochs and validators (permissionless staking, `node/src/staking.rs`, MAINNET-DESIGN 3.4):**
  - Genesis has `epoch_blocks`, an operator (owner, self-bond, commission) for every validator, and the staking parameters (`min_self_bond`, `max_validators`, unbonding, slashing, downtime). Dev and test chains may keep `validator_admins`.
  - Every validator owns a stake pool with share accounting: `delegate`, `undelegate` (unbonding for `unbonding_blocks`, then `withdraw_unbonded`), `redelegate`; rewards raise every share's value and the owner's commission is minted to it as shares. `register_validator` is permissionless (self-bond ≥ `min_self_bond`, proof of possession).
  - After executing the last block of epoch *e*, every node computes the set for *e+1* from state: the top `max_validators` eligible validators by pool stake (not jailed, tombstoned or removed; self-bond at least the minimum), ties by address; newcomers make up at most ⌊(m−1)/3⌋ of the new set (the members carried over finalize on their own while newcomers sync), ineligible members always leave, and it is never empty. Votes are one per validator.
  - Double-signing (simplex's own evidence, `report_equivocation`) slashes the pool and the stake that left it since that epoch began, pays the reporter a share, and tombstones the validator. Missing more than `downtime_max_missed` of its last `downtime_window` leader slots jails it until `unjail`. A block's unadmittable txs cost its proposer (CV-5), and verifiers replay unexecuted ancestors exactly before voting.
  - On dev and test chains, `approve_validator` pins a validator ahead of stake and `remove_validator` takes it out for good (admins only).
  - The set is part of state and of the state root.
  - At the boundary, the node `track`s the new peer set and starts a new simplex engine and scheme for *e+1*, with the boundary block as its floor. This follows the Commonware reshare orchestrator, minus the DKG.
  - Vote, certificate and resolver channels are muxed by epoch. A node that sees votes from a later epoch hints marshal to fetch our epoch's boundary finalization, so it catches up epoch by epoch.
  - Marshal spans epochs through an epoch-scoped scheme provider.
  - Nodes outside the active set observe (verify-only scheme) until their activation epoch.
  - CLI: `blockula validator init|register|unjail|commission|pop|approve|remove|list` for operators, `blockula stake show|delegate|undelegate|redelegate|withdraw` for delegators. `scripts/local-testnet.sh` onboards a validator by stake alone (init, faucet, register, selected at the next boundary).
  - API: `/api/validators`, `/api/staking/{account}`. The explorer has a Validators page with the set, candidates, jailings and slashes.
- **Mempool:** a tx submitted to any validator is checked against state + mempool, then gossiped to all validators on its own channel and de-duplicated by id. After each finalized block, included or now-invalid txs are evicted.
- **Faucet (testnets):** each validator's genesis-funded account pays its own faucet drips, so there's no shared secret and no nonce races. Full nodes forward faucet requests.
- `blockula summon <id> [--validators N]`, `blockula run --home`, `blockula dev` (one-validator simplex).
- **HTTP hardening:**
  - 128 KB request bodies.
  - Per-client tx rate limit. The client is the socket address unless `--client-ip-header` names the reverse proxy's header (e.g. `fly-client-ip`). Forwarded client IPs are honored only from `--trusted-forwarder` IPs or with `BLOCKULA_FORWARDER_SECRET`. IPv6 clients are counted per /64.
  - Faucet: 1 drip per address per hour and per client per 10 minutes, counted only on success. At most 32 drips pending, otherwise `503 faucet busy`.
  - Mempool: capped at 5,000 txs and 64 per sender, evicting the lowest fee-per-byte tx when full.
  - CORS stays permissive for the web wallet.
- **`blockula join --genesis <file|validator URL> --home <dir> [--genesis-hash <hash>] [--checkpoint HEIGHT:HASH[:SET_HASH]]`:** a non-validator full node. The genesis must be pinned (`--genesis-hash`, or compiled in for a known chain id), and the newest checkpoint younger than the weak-subjectivity period (OPERATIONS.md "Weak subjectivity"). It serves the API + explorer immediately (`/api/status` shows `syncing`, `sync_progress` and `finalized_height`). It pulls finalized blocks from validators over HTTP (`/api/sync`), checks the hash links and an ML-DSA quorum finalization certificate per batch, and executes them. It starts at a random peer, keeps to the fastest one (trying the next every 8 rounds) and benches for a while (60 s, doubling to 15 minutes) a peer that delivers blocks slower than twice the chain's rate, or, in a round a block time long, 4× slower (in blocks and in bytes a second) than another peer recently did, or that fails a round or stalls before answering "nothing new" (audit F27). A round counts as at least a quarter of a block time long, so a tiny round answered at once can't set a bar real batches can't meet; a peer with nothing new loses its rate; and a peer benched only for being slower keeps its rate as the bar while it waits and is free again once the faster peers stop delivering: when every free peer has said "nothing new", or a short round that left blocks behind is 4× below its rate (review-r2-sync-1). Batches never cross an epoch boundary, so each one is checked against that epoch's set, which the node learned by executing the previous boundary. Txs and faucet requests are forwarded to a validator.
- **Fast sync (default for `join` and new validators; `--full` replays from genesis):**
  - Every 100 blocks is a checkpoint C. Consensus requires the block at C+4 to carry `exec_height = C` and `exec_root = state_root(C)`. Every validator must have executed C and checked the root before voting; it waits up to 3 block times rather than vote unchecked. So any finalization certificate on C+4 or a descendant certifies `state_root(C)`.
  - Every node writes each checkpoint's state (canonical records → zstd → 1 MiB chunks, each BLAKE3-hashed) and keeps the two newest plus two long-lived ones: the first it wrote in each of the last two stretches of ~15 minutes of blocks (900 at 1 s blocks, `snapshot::long_interval`). It serves `/api/snapshot/latest` plus the chunks: the newest snapshot for a small state (up to 32 MiB compressed), the newest long-lived one for a bigger state, so a joiner has at least 15 minutes to fetch the chunks before they're deleted; `?min=` (the joiner's newest checkpoint) skips any whose manifest stops short of it (when none reaches it, the one reaching furthest is served, so the joiner waits for a newer snapshot). A pruning node's window covers every snapshot it keeps and the blocks after it.
  - The manifest carries blocks C+1..F, F's certificate, and the epoch anchor (the previous epoch's last block, where consensus starts the current epoch) with its certificate from that epoch's set when it's before C. The validator-set history comes separately, in `/api/epochs?from=` pages (about 2 MiB each) from the joiner's newest trusted root.
  - The joiner checks the set history from its newest trusted root (a checkpoint's pinned set, or the genesis), the certificates, the hash links and the C+4 commitment, and checks all of it against its trusted checkpoints. It keeps only the history it verified (root through F's epoch, nothing a peer listed past it) and checks it against the sets in the certified state. It then downloads and hash-checks the chunks, 4 at a time, spread over every peer it knows (any peer with the same snapshot serves the same chunks): a peer that fails a chunk (an error, a 404, a wrong chunk, or nothing within 30 s) isn't asked again, one slower than 10 s a chunk is asked only when nothing faster is left, and the whole download must finish within 2 s per chunk plus 2 minutes, or the joiner moves on to the next peer's manifest (peers are tried in a new random order each run). The history and the chunks share one deadline per peer: 2 minutes plus 2 s per epoch of history (at most 30 minutes) plus the download's budget; a manifest past the height the chain can have reached by the clock is refused before any history is fetched, and a history page that says there's more must hold a set change. It rebuilds the state, requires its root to equal the certified one, executes C+1..F and follows normally.
  - History before C isn't stored on that node; the explorer and `/api/block` say so.
- **Validator-set history:** when a boundary changes the set, members of the outgoing set sign a handoff `(genesis hash, chain, epoch, hash(outgoing set), hash(new set))`, retroactively too, but only for changes their own executed (or certified) state shows on both sides, never one a peer's registry lists. While a change lacks 2f+1 signatures here, nodes ask peers every 30 s for the `/api/epochs` pages from it and verify, off the chain lock, only signatures they lack (at most 512 per peer per round, up to a quorum per change). A joiner needs a 2f+1 handoff for every change after its trusted root. Unchanged epochs need no proof: hiding a change only makes verification fail. A node always keeps the weak-subjectivity window plus a quarter, and drops older changes once the history passes 8 MiB, so a joiner trusting a root older than that window (only possible with `--allow-stale-checkpoint`) may need a `--checkpoint` or an archive peer that kept it.

## Known limits

- Fast sync rebuilds before it can check. Only the snapshot's state root is certified, not the manifest's chunk list, so a malicious peer the joiner asks can serve chunks that decompress to up to `MAX_STATE_BYTES` (4 GiB) of tiny records (~140M), and the joiner builds the maps and the tree for all of them (tens of GB) before the root mismatch shows. A joiner with less memory dies and, restarted, tries the next peer. Until the checkpoint-certifying block also commits to a snapshot digest (the chunk-hash list and the record count, CRY-2), pin `--genesis-hash`, prefer known peers, and size joiners for the largest plausible state.
- Fast sync has a time budget. A snapshot lives at least 15 minutes after a joiner takes its manifest (100 blocks for a state under 32 MiB), so a joiner that can't download the state in that time gets 404s and moves on to the next peer's manifest (a newer snapshot), and after the last peer replays from the genesis; at ~5 MiB/s that covers the 4 GiB maximum. A joiner whose newest checkpoint is past the newest long-lived snapshot's manifest gets the newest snapshot instead, with only the 100-block budget. A peer that alone holds the snapshot its manifest names (an old one it kept) and serves each chunk just under the 30 s timeout, or pages its history slowly, holds the joiner until the attempt's deadline (its history budget, at most 30 minutes, plus 2 s a chunk and 2 minutes: ~2.8 hours at the 4 GiB maximum) before the next peer is asked. Each node keeps up to four snapshots on disk.
- Sync is weakly subjective, like any proof-of-stake chain: keys of a validator set that has since unbonded can sign handoffs to a made-up set (retroactively, and handoffs aren't slashable), so a joiner that trusts only the genesis could be fed an alternate history. Joiners pin the genesis (required) and recent checkpoints that fix a validator set (compiled into each release, or `--checkpoint`), and refuse roots older than the weak-subjectivity period: half the evidence window, ~10.5 days at genesis parameters (OPERATIONS.md "Weak subjectivity"). The checkpoints are only as good as the operators who agree on them and the release signature.
- The weak-subjectivity period follows governance as far as a node can know it (audit gap-6-1). Shortening the evidence window (`evidence_max_age_epochs`, the token holders' alone: a supermajority, never the council; `unbonding_blocks` can't fall below it) shortens the period, but never below a week: the window has a protocol floor of two weeks (`params::EVIDENCE_WINDOW_FLOOR_DAYS`, twice the weekly checkpoint cadence; a `ParamChange` below it is refused when proposed and when it runs, and mainnet's genesis must start at or above it). A node enforces the shortest of the genesis period, the one its release recorded (`weak_subjectivity_blocks` in `node/checkpoints/<chain id>.json`), the one its own executed state sets, and, before it syncs (`join`, and every start of a full node, which waits for an answer while its home is empty), the shortest any of its peers reports in `/api/status`. A report can only shorten the period and never below the floor, so a lying peer can at worst ask for a checkpoint a week old (or `--allow-stale-checkpoint`). What's left: a joiner whose every peer lies (an eclipse) after governance has shortened the window, on a release older than the change, accepts a root up to its release's period old (10.5 days at genesis parameters) where a week would be safe; keys that left the set more than a week ago could then feed it a forged history. A fast-synced node still warns when the installed state sets a shorter period than its root met (a forged state can hide it). Mitigations: list peers run by independent operators, use the weekly signed checkpoint, and releases cut after the change.
- A root's age is counted in blocks from the newest block whose time the node trusts (review-r3-sync-1): a checkpoint records its block's `timestamp_ms` (`HEIGHT:HASH:SET_HASH:TIMESTAMP_MS`, what `blockula checkpoint` prints; release checkpoints must carry it), so slots the chain missed before it don't make it look older. A checkpoint in the older forms (no time) gets its time from a peer's copy of its block (`/api/sync`, the consensus block, whose hash covers the time, so no peer can change it) when the home is empty; only when no peer serves that block (validators prune after about two days, full nodes keep everything) is it counted from the genesis, where every missed slot of the chain's life adds up: on an old chain with more than a week of them, such a checkpoint is then refused even at the tip once a peer reports the week's floor (or, past the genesis' 10.5 days, always), and the refusal asks for the timed form. The time is trusted like the hash: a node refuses one earlier than the genesis (or an earlier timed checkpoint) allows, later than its clock (plus an hour), a block at that height with another time, and later blocks earlier than it allows, so a wrong time fails closed against the real chain; only a forged chain built on a forged time gets past, which takes a forged checkpoint anyway.
- HTTP sync judges peers by what they deliver (audit F27, review-r2-sync-1), so a hostile peer can slow a catching-up full node, not stop it. While the honest peers are benched for failing, stalling or delivering below twice the chain's rate, a hostile peer holds the turn at just over twice the chain's rate (the node keeps up, and catches up slowly); one that has benched an honest peer by out-delivering it has to keep delivering a quarter of that peer's pace to keep the turn. Every peer can stall one round (up to the 30 s request timeout) each time it's tried, and is benched for longer each time. The constants (`node.rs`: 60 s to 15 minutes on the bench, 4× slower, a 120 s rate window, every 8th round tried elsewhere, a quarter block time per round at least) are to be retuned on the incentivized testnet.
- Hunts: awards are trusted to the creator. `blockula hunt award` checks GitHub before signing, but the chain doesn't. GitHub links are claims plus a per-node off-chain gist check (cached 10 min, 30 GitHub calls a minute per node). A handle with a verified claim can't be squatted (only the account its claims are credited to can link it). One that's squatted before its owner's first verified claim needs an admin, or on mainnet an `UnlinkGithub` proposal from the owner's account (a deposit burned without quorum, a vote and a timelock): it then holds the handle for the proposer for one voting period, and voters judge from the gist whether the proposer owns it. A link validators attest like a claim would remove that cost; it isn't built.
- Proof of Contribution v1:
  - **Season 0 trust.** On dev and test chains, admins bootstrap Soul, set repo weights, flag sybils, reject claims and claw back rewards. Chains without admins (mainnet) pull each lever only through a governance proposal (docs/GOVERNANCE.md). Validators are trusted to report GitHub honestly, merges and reverts alike (a BFT quorum must agree).
  - **Jury randomness** comes from the validators' commit-reveal beacon. A validator that sees everyone else's reveals can withhold its own, choosing between two values, so k colluding validators pick among at most 2^k draws. Each withheld bit costs the withholder `beacon_miss_slash_bps` of its pool (times one more for each miss in the last 64 epochs, at most 10%), the epoch it's caught in (the beacon step runs first at the boundary, so a jailed pool earns nothing for it) and the epoch it biased (the next set is selected without it; `Unjail` after `jail_blocks`, rejoining churn-limited), and a jailed validator can't commit to another round. What a bit buys is a choice between two leader orders for that epoch and, when a Séance opens at its end, between two jury draws, so at most that Séance's budget (a quarter of the contribution pool) is at stake: with a 10,000 FANG minimum pool, a first miss costs 10 FANG plus two epochs of the pool's rewards. A cartel that controls most reveals can still steer draws it values more than that; the bound only grows by governance raising `beacon_miss_slash_bps`. If no validator takes part (or all who do collude) the beacon is a predictable hash chain, and epochs 0 and 1 follow from genesis, so no Séance draws on them.
  - **Collusion.** Most of a jury agreeing to inflate a claim succeeds: Soul and juror agreement are measured against the jury's own outcome, which includes each juror's vote. Random audits of repos and reviewer–author pair flagging aren't built yet.
  - **Reverts** are found only within the ~30-day window, and only in the shapes validators look for: a commit with a line starting `This reverts commit <merge sha>`, or a merged PR whose description says that or `Reverts owner/repo#N` (`#N`, the PR's URL), whose diff undoes most of the PR's (up to 300 of its files read): more than half the lines it added and removed, removed and added back (a file renamed with edits may be renamed back, or its new name removed and its old one added back: audit review-fix-poc-3), and more than half of its files with no lines to compare (binary files, diffs too large for GitHub to show) whose pre-PR state is known brought back to it (a file it added removed, one it removed added back as the same blob, one it changed or renamed given back the blob it had at the commit the PR merged onto), never merely touched; a file the PR changed or renamed without a line that counts (only blank lines, a pure rename or mode change) is judged by its rename alone, never by its blob (audit review-r4-poc-1: one blank line in a file that later changes again made a reverted PR revert-proof); a PR with both needs both (audit review-r2-poc-1: removing the one README line of a PR that also added 20 icons isn't reverting it). Pre-PR blobs come from the base commit's whole tree (`git/trees/<base>?recursive=1`, one request however many files and directories: audit review-r3-poc-1); if GitHub truncates it (more than 100,000 entries or 7 MB of listing, which is about 30,000 files, since each entry takes some 200 bytes) or it's over the size cap, the files it doesn't name are looked up a tree level at a time, at most 16 trees, and a file the candidate changes whose pre-PR blob is still unknown counts as neither restored nor not (one it leaves alone wasn't restored), so neither the PR's layout nor a listing's cap decides; in such a repo a candidate that changes every one of those files is judged on the ones whose blob is known. A PR with nothing to judge (no lines, no file whose pre-PR state is known) has no revert attested. Since only the exact pre-PR blob counts, a revert that comes after another merged change touched such a file (a lockfile too large to diff, an image edited again) doesn't bring it back, and isn't attested unless the PR's other such files outweigh it; a claimant can use that on purpose (add a dependency, so the PR changes a lockfile too large to diff that later PRs change again) when the PR's other such files are few, and then only `reject_claim` catches the revert. Candidates come from the default branch alone, which only maintainers write: the newest 1,000 commits since the merge, the PRs of commits that look like revert landings, and the commits since the merge that touch the PR's files (up to 3 files, patched ones first, the newest 100 of each): those stating the revert in git's words themselves, and the PRs of the first 15 (audit review-r3-poc-2: a `git revert` pushed straight to the branch, with no PR, that a merge of many later-dated commits pushed out of the walk); not from the list of recently updated closed PRs, which anyone can flood. The claim PR's own commits are left out of all of that by sha, never by message (audit review-r2-poc-2: a revert's landing message is one the claimant can write in advance): the ones GitHub lists for the PR (250 at most) and every ancestor of the merge committed since it merged (`commits?sha=<merge>`, up to 1,000: the commits a merge commit brings along, however many, and a rebase merge's copies), which a later revert can't be. If those 1,000 don't hold them all and the walk reaches the merge, only commits the walk holds are followed through the files' histories. A commit message counts only in git's words, which nobody can write before the merge, and revert PRs written by the claim PR's author (descriptions can be edited after the merge) are tried last. Validators must agree on the same revert commit, so they all take the oldest on the branch whose diff checks out (at most 5 compared among candidates touching the PR's files, 10 fetched). A response over the 8 MiB cap (a claimant controls some: a squash message holds all its commit messages) is read again in pages of 10, then 1, and only an entry over the cap by itself is skipped, the same on every node, so `Err` (try again later) means GitHub couldn't be reached or answered with an error (rate limit, outage), not anything a claimant can shape (round 2 said this before the commit listings were covered). What can still hide a revert needs maintainers to merge it: a merged PR bringing over 1,000 commits dated after the revert pushes it out of the walk, and then only the files' histories find it, which more than 100 later commits touching each followed file push it out of too (validators keep the attestations they've made, so a flood must land before most of them check after the revert, within the hour); a claim PR of more than 1,000 commits whose extra ones also reach the branch through another merged PR; or later merged PRs (the claimant's included) whose commits touch the files and state the revert without undoing it, five of them ahead of the real one. A revert outside those shapes still needs `reject_claim`, and a revert-rejected claim's PR can't be claimed again. Dev chains (`claim_maturity_blocks` 0) have no window.
  - **GitHub rate limits:** each validator makes 2 GitHub calls per pending claim, and re-checks each claim in its revert window hourly (about 6–13 calls; at most about 105 when the branch is busy, the PR is large, revert candidates show up and GitHub truncates the base's tree, plus up to 110 for each list page whose entries are near the size cap), 4 claims a minute at most (set `GITHUB_TOKEN` on validators). If GitHub is unreachable, claims stay pending and are refunded after ~7 days.
  - **Volume and identities.** Rating a person's claims together (one win rate pooled over all their comparisons) and ranking them (each after the first a quarter of the one before) bounds what volume adds within one Séance to a third, in expectation; one Séance's draw can still rate a pile of weak claims above its true quality, as it can one claim, and a pile rated just over the 15% threshold clears it more reliably than one such claim (more comparisons, a steadier rate), for a fraction of a solid PR's payout. It doesn't stop spreading claims over Séances (each is then judged on its own against that week's field), and like any per-person damping it makes splitting one person's work across several identities pay more than the square root did: those identities each need a GitHub handle with merged PRs and Soul or a vouch, the voucher answers for them (`FlagSybil`), and each counts as a person toward the budget's scaling (`FULL_BUDGET_PEOPLE`). A person's second and third PRs of the same quality in one Séance add 25% and 6%, and weaker ones lower the person's rate for all of them, so someone with one standout PR and several minor ones does better claiming the minor ones in a later Séance, and prolific contributors do better claiming as their PRs mature than in batches.
  - **Funding:** 20% of issuance each epoch, the endowment's vested stream, donations and slashed bonds. On a young chain with little staked, the stakers' share can't all be placed and the rest goes to the treasury.
  - **Cost:** the contribution state is hashed whole into every block's state root (like Hunts), and some lookups scan all claims or grants.
  - **Attestation fees** come from the validator's owner when it has a separate one (SF-13: the consensus key signs with `from` = the owner, with no tip), else from the consensus key's own account. `BLOCKULA_SYSTEM_FEES=self` makes the consensus key's account pay regardless (the owner's nonce is shared with whatever else signs for it).
  - **Mempool estimates:** admission dry-runs a tx after its sender's queued txs on the executed state, not through the end-of-block steps of blocks still being finalized. That only delays or fails a tx (fee charged); it doesn't affect consensus. (Proposals and verification replay unexecuted blocks exactly, end-of-block steps included.)
  - **Default timings are consensus rules.** Chains whose genesis omits `contribution` (the public testnet included) take them from code, as they do every constant in `poc.rs`, so changing them is a coordinated upgrade.

- **The PQ p2p transport is a vendored fork.** The hybrid X25519 + ML-KEM-768 handshake lives in a patched copy of `commonware-stream` 2026.9.0 (`node/vendor/`) until Commonware ships a pluggable KEM (#5183), and nodes on the older X25519-only transport can't peer with it. The public RPC's TLS is only post-quantum behind an edge that negotiates `X25519MLKEM768` (Fly's didn't when measured), and HTTPS certificates are still classical ([PQ-TRANSPORT.md](PQ-TRANSPORT.md)).
- A validator's consensus key signs its system txs for its owner (SF-13), who pays their base fee, out of locked tokens too (a vesting allocation can run a validator), and for a multisig owner without its threshold. It can't tip (audit F04/F06), so it moves nothing to anyone, and what a stolen one can make the owner pay is bounded by the validator's duties (audit F04): such a tx whose action would fail isn't admitted (never charged; a proposer that includes one anyway pays for it as junk), it updates the validator for its owner at most once an epoch (and never changes its terms or unjails it from the validator's own account when the owner is another account: audit review-r2-integrate-compose-1), and once the validator is tombstoned or removed it signs only a reveal for a commitment made while active. That leaves, each epoch, one `UpdateValidator`, a beacon commitment and a reveal, a readiness signal or an admission while the set is one or two members, an attestation per claim (and per claim in its revert window) the validator may attest, and a report per real fault: a few base fees, burned, plus the owner nonces those txs take (the owner's own txs wait behind them, and are dropped with one that stops applying first, such as an attestation of a claim other validators settled: [OPERATIONS.md](OPERATIONS.md)). It could do worse by double-signing. Protocol v1 has no owner-signed rotation or revocation of a consensus key and no on-chain opt-out of SF-13 (`BLOCKULA_SYSTEM_FEES=self` is a node setting: a stolen key ignores it).
- Validator duties' mempool lane (audit F32/F56) is local policy: a proposer that doesn't run it can leave duties out (the next honest leader includes them). The lane is a prefix of each sender's queue (so a duty can't shield the txs ahead of it from eviction), so a validator's duties queued behind other txs from the account that pays them (the owner's own untipped txs, a testnet faucet's drips from the validator's account) are ordinary untipped txs until those leave the mempool: refused while it's full, and proposed after every tipped tx. An owner account that already has 64 txs queued refuses them outright, and so does one with a shield queued (once Ghost Mode is on, a shield is its sender's last queued tx: review of F36, round 3) until the shield is included: shield from another account. A testnet faucet's drips share the duties' queue only where the consensus key's account pays them (a validator that owns itself, as on `blockula dev` and `scripts/local-testnet.sh`, or `BLOCKULA_SYSTEM_FEES=self`); the public testnet's validators have owner accounts of their own, which pay the duties, and drip from the consensus key's (`deploy/launch.sh`). A candidate's readiness (`ValidatorReady`) and a member's admission (`AdmitValidator`) are duties while they'd apply, so the node's own readiness never holds back the duties queued behind it (review-r2-consensus-2).
- Ghost Mode (once governance activates it): a queued shield is its sender's last queued tx, so an account with a shield waiting sends nothing else until it's included, leaves the mempool (evicted for a higher tip, expired, or after `MEMPOOL_TTL_BLOCKS`, 600 blocks) or is replaced by the account's own shield at the same nonce for a higher tip (noted "replaced by its sender's shield with a higher tip"). That's what lets a full ghost share always give a shield up for a higher tip without leaving a nonce gap (review of F36, round 3). Wallets shield last.
- Peers' claimed tips are display-only (`/api/status`'s `network_height_claimed`, `/api/health`'s "syncing"): a majority of a node's HTTP peers can make it look behind, but validator duties wait only on finalized heights the node verified (audit F11).
- Voting power is one vote per validator (stake decides who gets a seat, not how much it weighs: simplex's quorum counts signers, DEC-3).
- Insider seats (audit xcut-economic-2) are bounded by account: locked stake ranks only its holder's own pools, an account with unvested tokens takes at most one seat as a newcomer, and the founder's and the foundation's accounts (`bootstrap_excluded`, fixed in the genesis) together at most 2 and fewer than f. The chain can't tell who controls an account, so an insider's vested (liquid) tokens, once it has some, back validators like anyone's, and genesis operators that pool their grants hold one seat each, as they already did. Seats held before a rule binds them (genesis seats) aren't taken away.
- The bootstrap delegation (DEC-5) moves its stake between pools at epoch boundaries without unbonding: stake it took out of a pool isn't reached by equivocation evidence for an earlier epoch that arrives later (the operator's and other delegators' stake still is), which only spares the treasury. Its eligibility rule is the next set minus the founder's and the foundation's accounts; DEC-14's hosting caps aren't on-chain for validators that join after genesis.
- A candidate connects over p2p as a secondary peer once it's eligible and among the likeliest to join (capped, so the peer set stays under the p2p layer's limit). It syncs via marshal and votes once caught up; until then it counts as offline, which the churn limit bounds.
- A set that shrank below four (jails, tombstones, under-bonded members) regrows by one newcomer per epoch on chains without admins (audit F24). Into a set of 2 or 3 the newcomer is past the churn limit and needed for every quorum (f = 0), so stake alone can't buy the seat (audit review-fix-staking-2): it joins only if a quorum of the members it joins (both of two, the one of one) admitted it in that epoch, each by its operator's decision (`AdmitValidator`, `blockula validator admit`; nodes never send it), and its consensus key signaled readiness in the epoch's last tenth (`ValidatorReady`, sent by its node once admitted). A stranger that outbids every candidate can't get in, nor can an admitted candidate whose node is down at the end of the epoch. What's left is trust in whoever the members admit: a newcomer that is admitted and then stops voting halts the chain for good, as each existing member of such a set could. Without blocks there's no epoch boundary, no jailing and no governance, and restarting nodes doesn't change the active set in state, so only a hard fork (state surgery or a new genesis) recovers. Readiness shows the key's holder signed in the window, not that its node keeps running. Admissions count for one epoch, so the members must agree within one (OPERATIONS.md, "A set of one or two"). The alternative, a set stuck at one or two members, has no recovery short of a hard fork either.
- Equivocation is caught only if some honest node sees both votes; reports are best effort (each node keeps its evidence in `evidence.json` until the chain acts on it).
- Slashing protection's restart escape (a validator signing on its record alone after ~20 s without certificates) needs its HTTP peers to show the network standing still at its height (audit F18). Their `/api/status` answers aren't signed, so the rule counts them: peers at its height must outnumber those claiming more, and a peer that claims more is asked to prove it with certified blocks. Safety side: a validator restored from an old volume escapes anyway if the peers that answer at its height outnumber the honest ones ahead, none of those can prove it (they pruned the blocks after its height, or it can't reach their `/api/sync`), and fewer of its epoch's validators than can be faulty reach it over p2p with later-epoch traffic; an eclipse, in short. Liveness side (review of F18): no single unverified source can keep a restarting network halted (one validator's later-epoch traffic is outvoted and expires; one lying HTTP peer is outvoted), but a validator whose HTTP peers claiming to be ahead aren't outnumbered keeps abstaining until its operator starts it with `--network-halted-at H`, which overrides unverified answers (OPERATIONS.md, coordinated restart). And the escape stays the one case a restored disk could double-sign: views after the network's last finalized block that its earlier run voted in (OPERATIONS.md: never restore a validator volume).
- If every genesis validator is removed, new nodes still bootstrap from genesis addresses plus the active validators in their *local* state. A brand-new node then needs at least one genesis validator to be reachable, or to start from a peer's copy of the chain.
- Simplex journals are kept for the current epoch and the two before it (older ones are deleted). State keeps the validator sets of the evidence window (`evidence_max_age_epochs`, at least 8 epochs), so `/api/sync` can only certify batches from those epochs for nodes that are far behind.
- Rate limits are in-memory and per node, so restarting a node resets them, and each node in a pool counts separately. No proxy header is trusted by default. A configured `--client-ip-header` is read from the right (`--client-ip-hops` appending proxies), and a request without a usable one is limited as the proxy itself, never as an unlimited local caller.
- `join` fully backfills from genesis over HTTP and trusts no single peer (certificates are verified), but there's no snapshot sync yet. Full nodes don't serve `/api/sync` themselves.
- Behind NAT (e.g. Fly dedicated IPs), peers see the NATed source address. If the recommended preset rejects such peers, run with `--p2p-preset local`.
- The state root covers state *before* the block it's embedded in (deferred execution), so a block's own post-state root is in `blocks.jsonl`, not in the certified consensus block.
- If `consensus/` is ahead of `blocks.jsonl` (e.g. `blocks.jsonl` deleted), the node logs an error; delete `consensus/` to resync.
- The state root is a flat hash over all state, computed once per block (~10 ms per 100k accounts). Phase 1 moves to a Merkle tree for light-client proofs and incremental roots.
- Txs apply through an undo journal; nothing clones the state per tx. Mempool admission dry-runs a tx after its sender's queued txs (in nonce order, as a block runs them), so a tx that can't execute after them (behind a key removal, past a session limit) never takes a slot. Each recently active sender's simulation is kept (a structure-sharing copy of the state, rebuilt once per block), so admission costs one dry run per tx whatever the size of the mempool or of the queue.
- Mempool admission's dry run isn't unwind-safe. With nothing of its sender's queued, it runs the tx on the live state and rolls it back through the journal on success or failure, but a panic inside the state machine (after the fee phase moved the fee and the nonce) unwinds past the rollback, and nothing catches it, so the node's state would silently diverge from the chain. The state machine is meant never to panic on any input: overflow checks are on in release builds, so a missed bound is a panic rather than a wrap, and the same panic in a block would stop every validator anyway (review-r2-gov-1 was one: the upgrade checks saturate now). A dry run on a copy, or one under `catch_unwind` that reloads the state from disk, isn't built.
- Upgrade governance (audit round 4):
  - **Superseded numbers aren't spent.** A cancellation spends the versions it withdraws and those of upgrade proposals that had passed; the numbers of proposals it supersedes while they're still being voted on (unless they pass anyway: those spend their numbers when their vote closes), or waiting in a multisig for approvals, aren't spent (filing one mustn't spend numbers), though a release may carry them. The chain advises past them (the cancellation's outcome, `/api/upgrade`'s `next_version`, review-r3-gov-1) but still accepts them, so reusing one is the release team's call (OPERATIONS.md "Withdrawing a scheduled upgrade": never reuse a number a release was published for). Conversely, anyone can push the advice up by at most 16 numbers per cancellation (an upgrade proposal, or a multisig's stored one, at the top of the version step while the cancellation is pending); nothing is spent and the step moves with it. A multisig's stored number past the step doesn't count at all.
  - **A timelock raised mid-vote** makes a proposal run later than when it was proposed, so one at the near edge of a lower bound (an upgrade activating at least 64 blocks after it runs and leaving room for a cancellation, a claim deadline after it runs) can fail when it runs, and has to be proposed again; propose with a margin. The upper bounds (an activation at most 365 days, a claim deadline at most 730 days out) count from the proposal's vote end, fixed when it's proposed, so a timelock lowered mid-vote no longer fails a proposal at their edge (review-r3-gov-3).
  - A cancellation scans every multisig proposal stored at the time (once, when it runs) for the upgrade proposals it supersedes.
- Failed actions are charged their fee. A failed tx keeps its place in the block, flagged in `failed`.
- Names can be front-run by a proposer. Mempools admit only the first account's registration of a name while it can be included (its fee covers the next base fee) and for `NAME_HOLD_BLOCKS` (17) after it arrived, so outbidding a registration seen in the mempool doesn't work through honest nodes. A registration wrapped in a multisig action counts too: a `MultisigPropose { RegisterName }`, or a `MultisigApprove` of a stored one, is refused while another account's registration waits, and holds the name itself while it would run the registration in the next block (a 1-of-1 proposal, or the approval that reaches the threshold). A k-of-n multisig's registration holds the name only from that last approval on, so a multisig that wants its name should propose it, then send the approval that completes it promptly (its owner keys can't tip). A validator can still put its own registration of a name it saw first in a block it proposes (the other one then fails, charged, as "already taken"), and someone who reaches a node before the first asker's tx does can win the race there. Registering with a commit-reveal (commit a hash, reveal the name a few blocks later) would close both; it isn't built, since it costs every registration a second tx and a wait. Until then, send a registration that matters to a node you trust, with a tip so it makes the next block.
- Transfers that create a new account must carry at least 0.01 FANG.
- `exec_root` is still a best-effort check. Each block must cite a state root at most 16 heights behind the verifier's executed height, and verifiers that have executed that height check it. A root that no honest verifier has executed yet goes unchecked until one has.
- Storage:
  - Marshal keeps 2,000 heights of blocks and certificates and prunes the rest.
  - Every node keeps all consensus blocks (`cblocks.bin`) plus finalization certificates every 100 heights, at epoch ends, and once 1 MiB of blocks has gone by since the last one kept (`CERT_SPACING_BYTES`), so it can serve verified `/api/sync` batches however full the blocks are.
  - Only the last 2,048 executed blocks and 1,024 certificates stay in memory.
  - A node whose consensus storage predates this layout must re-sync (`consensus.version`).
- The faucet is rate limited per address and per client (/64 for IPv6), checked and recorded in one step (parallel requests can't slip through), but a determined attacker with many IPs can still drain it slowly. CORS stays open because the wallet and SDK call it from other origins, so a web page can spend its visitors' per-IP budgets (each drip still needs a fresh address). It's for testnets only (no faucet on mainnet, DEC-10).
- The CLI pins the chain a node is on (chain id, genesis hash, prefix; `node/src/cli_net.rs`) and signs `.boo` names as names wherever the chain resolves them. Where an address is needed it takes one: a name in `--from` is resolved by the node (printed as unproven) off mainnet and refused on mainnet, in every command (`validator commission`, `admit`, `unjail` included), and `validator admit` takes only the candidate's address, on every chain. Within the pinned chain it still trusts the one node it signs through for the nonce, the fee quote and the height its tx's validity window starts from. That height is refused when the chain can't have reached it by this machine's clock, counted from the pinned genesis's start and block time, with 15 minutes for clock error (round 4, review-r3-clients-2). A chain that ran slower than its block time leaves that much room, though, so a hostile node on the right chain can still hold a signed tx and release it later, in a window it chose within that room. Use nodes you trust for anything that matters.
- Without witnesses (the SDK and MCP by default, the web wallet unless `NEXT_PUBLIC_*_WITNESSES` is set), every client signs the name itself wherever the chain resolves it (payments, hunt awards, vouches, Soul grants, flags, clawbacks, name offers, proposal targets). A lying node can't point such a tx at another account when it's signed. The chain pays whoever owns the name when the tx runs, though, so a name that changes hands or lapses (after its grace period anyone can register it) between signing and execution pays its new owner. A hostile node can pick when that is: the tx's validity window counts from the height the node reported (audit review-r3-clients-2). The SDK refuses a height ahead of its witnesses' heads (with witnesses it signs the proven address anyway) or of a `genesisClock` pin. The MCP and the web wallet refuse a height the chain can't have reached by its genesis clock (the MCP's built in with a known genesis; otherwise the node's `/api/genesis` taken on first use, like the genesis hash, and remembered with it: in `known-chains.json`, or in the browser's storage), so it binds a node that turns hostile later, not one that lied from the start, and leaves the same room as the CLI's for a chain that ran slower than its block time. Pay a name that's close to expiring by address. The structural fix is a format change left for a later protocol version: a time-based expiry, or a recent block's hash, in the signed tx.
- Where an address is needed (staking's validator, the account `actAs`/`use_account` acts for, a key grant's account), a name is one node's unproven answer. It's shown as such on test chains and refused on mainnet until the user confirms the address (SDK `UnprovenNameError`, also for a resolution passed to `build`/`keyGrant`; MCP `needs_confirmation`, on any node pinned to `blockula-1` whatever the MCP's configuration calls it; the web link page's check step). A confirmed address is only as good as the user's check of it.
- What a vote, a multisig approval or a sealed Séance judgment binds is what the signer's client shows them (audit gap-7-6, review-r2-clients-2/3). Every client describes a proposal, a multisig action and a juror's pairs from the content the digest covers (`describeKind`/`describeAction` in the SDK, the web governance page and the MCP; `blockula gov list|show`, `multisig show`, `contrib seance`), with the digest, and never presents the node's own `summary` as what something does: no digest covers that text, so a node can make it say anything (it's shown at most as the node's labelled note in `gov show` and `multisig show`). A node that shows one thing and answers the signing read with another is refused before anything is signed: the MCP's `vote` takes the `proposal_digest` `list_proposals` returned, and the CLI's `gov vote`, `multisig approve` and `contrib vote` take `--digest` (without it they print what they bind and ask; `--yes` without `--digest` signs whatever the node answers then, for scripts that trust their node). What isn't bound, and stays the reader's to check: what the pages behind a link say (a proposal's URL, a PR's diff), the proposer's own words (titles and reasons, shown quoted), whether a full address shown as a recipient is the one the user means, anything a client can't read exactly (a number past 2^53 in JS: no digest, so no vote from the web or MCP; use the CLI), and the node's word on everything around the content (tallies, status, the proposer's label, a multisig's approval count), which a lying node can still misstate to sway a voter. A multisig's pending `vote` binds its proposal by digest, not id: `multisig show` and `multisig approve` read the proposal and describe it only when its content has that digest, and otherwise say not to approve (`approve` refuses), and the SDK's `reviewAction(action, { proposal })` does the same (gap-7-6, round 4). An approval counts on the account it's signed from, which no digest binds: `multisig show <name>` prints the account as given and the node's address for it as UNPROVEN (never as the `--from` to copy), and `multisig approve` checks that the node answered for the account it signs from and asks to confirm one found by name (review-r3-clients-6). The web wallet has no multisig view; the SDK's `multisigApprove(id, { action })` binds the action its caller passes, on the wallet's own account.
- Some signed values still start from one node's report, bounded (audit gap-7-3, gap-7-5): absolute expiries (a session key's, a hunt's, a distribution's claim deadline) count from the height the tx's `valid_until` does, so a node lying about the height stretches them by at most the validity window (`max_tx_validity_blocks`, 600 blocks in the CLI); `propose`'s default deposit is at most `maxDeposit` / `--max-deposit` (1,000 FANG) and must match the client's witnesses. Within those bounds a lying node still chooses: pass `deposit`, or use witnesses you trust. Unstaking an amount takes nothing from a node: the MCP, the web wallet, `undelegate(v, { amount })` and `blockula stake undelegate --amount` sign the amount and the chain converts it at its own price (round 3; until then the conversion used the node's value of the stake, and a node reporting a little more than the amount, or many more shares, turned a partial unstake into all of it). Unstaking `all` signs the share count the node reports, so a lie there can only unbond less than all, or fail on chain. `sharesFor` (for `redelegate`, and `undelegate` by shares) is still the node's value.
- A key's consent to an account (`AddKey`'s proof of possession) doesn't expire and isn't tied to a nonce: once given, the account's owners can re-add the key with it after removing it. Only accounts the key agreed to can list it in `/api/key`.
- `sdk-ts/src/passkey.ts` typechecks but hasn't been exercised in a real browser yet.
- Proven reads (`provenAccount`, `provenName`) trust their witnesses for the state root, and bound staleness by the heads the node and the witnesses report: a proof may be up to `maxLagBlocks` (10 by default) behind. Witnesses that all lag (or collude) can still make old state look current. Roots certified by a finalization certificate would remove that trust.
- The MCP's spending caps are its own, client-side: they count what it signs (reserved before sending, pending txs included) at prices its pinned node reports, computed from `/api/params` and never below `/api/name`'s quote, so a lying node can understate a name's price. Only a session key's limit is enforced by the chain (and session keys can only send transfers). Chain text is labeled `untrusted_*` and cleaned, which helps an agent resist prompt injection but can't guarantee it; the caps and the session key's limit bound what a fooled agent can spend. Two MCPs sharing `BLOCKULA_HOME` share one ledger (a lock file serializes them). `tx_status` reads a tx it signed that the node can't show (a pruned block, a fast-synced node) against the account's nonce and the head (audit review-r3-wallet-1): with `BLOCKULA_WITNESSES` the nonce is proven; without, `expired` ("its nonce was unused past `valid_until`: it never ran") is the node's word, so a lying node can call a payment that went through expired, and the answer says to check another node before signing it again. With witnesses only the nonce is proven: which tx used it (a sibling's status, the node's 404 and `history_from`) is still the node's word, so `nonce_used`'s "this one most likely never ran" can be a lie too, and the answer says so. Records in `agent-txs.json` name the chain they were signed for, so a tx signed on another network (or before a relaunch) is answered `other_chain`, never read against this chain's head and nonce (review-r4-wallet-3).
- Supply chain (audit round 2):
  - **The one-line install trusts the script it downloads** (audit F49). `curl … | sh` runs the release's own `install.sh`, which a compromised GitHub account or release workflow controls, along with any release key id built into it. Its checks protect against a swapped or corrupted download, not against that adversary. It's for developers. Validators install and upgrade with `blockula release install` (docs/OPERATIONS.md "Installing and upgrading"), which checks the release against the release key id pinned at their first install and never runs anything from the release before that check passes.
  - **A first install trusts the announcement** (audit F49, review-r2-supply-1, review-r3-supply-4). With no `blockula` on the machine, nothing there can check the ML-DSA signature, so the first binary is trusted because its archive hashes to the SHA-256 the signer announced in the operators' channel (or because it's a copy of a binary you verified on another host). An operator who takes the archive hash from a channel the attacker controls runs the attacker's binary, which can pin anything; every later upgrade then trusts that key. Once the key ceremony has built the release key id into the binary, the key id alone isn't enough: the genuine binary refuses to pin (`install`, `fetch`, `pin`) or verify against any other key id, so an attacker who swaps only the key id in the docs gets a refusal that names both. A key that legitimately replaced the built-in one comes in only through the rotation statement the built-in key signed. Before the key ceremony there's no release key and nothing built in, so whatever key id is given is pinned unchecked; the runbooks say not to use `release install` until the key exists. Take the archive hash from a channel GitHub doesn't control.
  - **What the release signature vouches for** (audit F49, review-r2-supply-4). The signer checks that the tag is the commit they reviewed, that the Linux archives rebuild bit for bit (two builders), and that `install.sh` and the genesis and checkpoint files are that commit's own (`scripts/check-release-files.sh`). The macOS archives are signed on provenance unless someone rebuilds them with the release run's Xcode, so a compromised release workflow could get a macOS archive signed. The signer's "reviewed commit" is only as good as their review of it.
  - **A release key compromise** is recovered by rotation, not prevented: whoever holds the key can sign a release, and a rotation statement (`blockula release pin --rotation`) moves the pin only if the pinned key signed it, so a stolen key can also rotate pins to the thief's. Operators cross-check a rotation on a channel GitHub doesn't control. There's no revocation list.
  - **GitHub settings aren't in code** (audit supply-chain-B-3). `deploy/github/` holds the intended rulesets (applied on 2026-10-17, and matching), and CI keeps the workflows in step with them, but only the admin can apply them (`deploy/github/apply-rulesets.sh`). A daily job (`github-settings.yml`) reports drift on GitHub's side within a day, without the bypass actors, which a read-only token can't see. `check-required-checks.mjs` reads the workflows as GitHub does (a YAML parser; what it can't read the same way is refused), so no required job can skip itself, depend on an optional one, or be stood in for by another job's check; it doesn't judge what a step's command does (`run: … || true`), which is code review's. With one maintainer, every PR merges through the admin bypass, so code-owner review doesn't bind that maintainer until a second one joins.
  - **Fuzz crashes are sealed, not hidden** (audit supply-chain-B-1). A red nightly job still tells everyone which target crashed that night. The corpus cache isn't secret either (fork PRs can restore the default branch's caches), though it never holds a crashing input. Without `FUZZ_CRASH_AGE_RECIPIENTS` set, a crash isn't kept at all and has to be found again privately.
