# Blockula mainnet readiness

As of 2026-10-14, v0.4.0 (commit `b1f9614`; line numbers refer to it). This is the gap between today's public testnet and a mainnet that holds real value. Every claim cites code or a doc section so it can be re-checked. Items marked ✅ were fixed after this assessment was written.

For the current v1 testnet rollout and the evidence required before choosing a mainnet launch
date, see [LAUNCH-PLAN.md](LAUNCH-PLAN.md). The assessment and estimates below retain their
original baseline; a scripted relaunch is not evidence that the public deployment has happened.

- **Paths:** Rust files are in `node/src/` and cited by file name (`chain.rs:1489`). Everything else is relative to the repo root. Doc sections are cited by heading (PLAN.md "Known limits").
- **Effort:** S ≤ 1 engineer-week · M 2–4 engineer-weeks · L 1–3 engineer-months · XL > 3 engineer-months.
- **Who:** Team (we do it in code) · Auditor · Counsel · Operators (independent validator operators) · Upstream (Commonware).

## 1. Verdict

Blockula is a solid testnet and not close to a responsible mainnet. Expect about a year with 2–3 engineers (Q3 2027 at the earliest), or about 9 months with the scope cuts in section 6. Most of the remaining work changes consensus formats, so it has to land before an audit can start. The critical path:

1. A persistent, Merkle-committed state layer (CV-1).
2. Stake-weighted validators with slashing (CV-2, CV-3), a multi-party replacement for the single admin key (GOV-1), and height-gated upgrades (OPS-3).
3. A consensus-format freeze, then external audits, then at least 3 months of incentivized testnet run by independent operators.
4. A genesis ceremony with keys generated independently by each operator.

Legal review, the post-quantum handshake, supply-chain hardening and wallet recovery run in parallel, but all must be done before genesis.

### Security & audits

**SEC-1. No third-party audit.**
- **Missing:** only an internal review exists (README.md "Status"; docs/ONE_PAGER.md:32). The riskiest code is ours, not a library's: the ML-DSA certificate scheme plugged into Commonware (`pq.rs`), block verification and the checkpoint rule (`consensus.rs:346-412`), the state machine (`chain.rs`, `poc.rs`), fast-sync trust (`snapshot.rs`, `epochs.rs`), and Rust/TS signing parity (`types.rs:222-386` ⇄ `sdk-ts/src/tx.ts`).
- **Why it blocks:** one consensus or accounting bug loses funds or splits the chain, and nobody outside the team has looked.
- **Done when:** a firm with BFT and Rust experience has audited the frozen genesis commit (node, consensus integration, state machine, sync, crypto use). A separate review covers the wallet, SDK and MCP (WAL-3). All critical and high findings are fixed and re-verified, and the reports are published.
- **Effort:** L. It takes 6–10 weeks of calendar time including fixes, and firms book 1–3 months ahead, so reserve a slot now. **Who:** Auditor.
- ✅ **Early independent findings (wave 3):** of the 12, the Ghost Mode ones (#5, #6, #8, #9) are fixed in `node/ghost`. P-HARDEN fixed #10 (HIGH: txs that could never execute held mempool slots for free, see TOK-2), #11 (MEDIUM: an unbounded hunt record made every later snapshot unreadable; every nested collection is now capped and every record checked against the snapshot limit), #1/#3 (MEDIUM: nothing bound the node to the hybrid p2p transport, see CRY-1) and #7 (LOW: txs replayed on a relaunch that kept the chain id, see WAL-5), each with a regression test reproducing its PoC. #12 (INFO: fast sync rebuilds a peer-chosen state before the root check) is documented in PLAN.md "Known limits" until CRY-2 certifies the manifest. #2 (INFO: the p2p handshake and txs both sign with an empty ML-DSA context) and #4 (INFO: ml-kem leaves stack copies of KEM secrets) are accepted as notes for SEC-1's scope.

**SEC-2. The PQ crypto libraries are unaudited.**
- **Missing:**
  - `ml-dsa = "0.1.1"` (`node/Cargo.toml`) says in its README that it "has never been independently audited". It signs and verifies every vote, certificate and tx in the node.
  - `@noble/post-quantum ^0.7.1` (`sdk-ts/package.json:24`) says it "has not been independently audited yet" (self-audited at 0.6.1). It signs every tx from the SDK, MCP and wallet.
  - Commonware is pinned (`=2026.9.0`). Nobody has checked whether the modules we use (simplex, marshal, p2p discovery, stream, storage) are covered by its audits.
- **Why it blocks:** a verification bug, or a disagreement between the Rust and TS implementations, is a key-forgery or chain-split bug.
- **Done when:**
  - NIST ACVP known-answer tests for ML-DSA-65 keygen, sign and verify run in CI for both implementations.
  - A cross-implementation test signs in each and verifies in the other (extending the vectors at `types.rs:755-788`).
  - SEC-1's scope explicitly covers our use of both libraries, or we switch to audited ones.
  - Crypto dependencies are pinned to exact versions.
- **Effort:** M. **Who:** Team, Auditor.
- ✅ **Wave 1:** ACVP and Wycheproof KATs for both implementations, Rust ⇄ TS cross vectors (v3 txs and their wire form, votes, PoP, handoff, `tboo` addresses) and exact pins, in CI (`.github/workflows/crypto.yml`; `kat.rs`, `sdk-ts/test/kat.ts`). Pending: the audit (SEC-1).

**SEC-3. No fuzzing, invariant checks or Byzantine tests.**
- **Missing:**
  - Nothing in `node/src` is fuzzed or property-tested.
  - The FANG conservation check exists only as a test helper (`poc.rs:1500-1511`).
  - The simulator covers honest crashes, onboarding and fast sync (`sim.rs`), not misbehaving validators.
- **Why it blocks:** every network-facing decoder takes attacker input: `CBlock::read_cfg` (`consensus.rs:143-185`), tx JSON plus `check_format` (`types.rs:401-579`), `/api/sync` batches (`node.rs:555-585`), snapshot manifests (`snapshot.rs:150-193`) and finalization certificates. So does the state machine. A panic or divergence in any of them halts or splits the chain. A read-through found no panic in the decode paths, but a read-through is not evidence.
- **Done when:**
  - cargo-fuzz targets exist for each decoder, plus a "random txs → apply → `conserved()`" target. They run in CI and for at least 2 weeks on dedicated machines without findings.
  - Conservation and nonce invariants are asserted after every block in the simulator.
  - Simulator scenarios use Commonware's deterministic runtime and simulated network to cover an equivocating leader, a wrong `exec_root`, junk-tx blocks (CV-5), withheld votes, partitions and clock skew.
- **Effort:** L. **Who:** Team.
- ✅ **Wave 1:** `node/fuzz` (8 targets: blocks, tx JSON and wire form, manifests, state records, sync batches, epoch registries, certificates; nightly in CI). Its two findings, FUZZ-1 and FUZZ-2 (epoch-0 panics in fast sync and in the epoch exchange), are fixed with regression tests. `State::check_invariants` runs after every block in tests and the simulator, plus property tests over random tx sequences. Pending: the 2-week soak, a state-machine fuzz target, the Byzantine scenarios.
- ✅ **Wave 3 (P-HARDEN):** a 9th target, `state_machine` (nightly in CI too): fuzzer-chosen sequences of txs of every tag (any wire-encodable action included) from users, agent session keys and the admin validator, in blocks across epoch ends and Séances. After every block the incremental root equals a full rebuild, a rolled-back dry run leaves no trace, and `check_invariants` holds (conservation, escrows, cross-references, and now every nested collection's cap and every record's size); the final state survives the snapshot encoding and replays to the same roots. About 120,000 executions in 27 minutes found nothing (node/fuzz/README.md). Simulator scenarios (`sim/byzantine.rs`): a 2–2 partition (no quorum: nothing finalizes for 30 s, then the chain resumes), a 1–3 partition (the majority goes on, the isolated validator catches up), clock skew within and beyond `MAX_CLOCK_DRIFT_MS` (SF-2), and one, then two validators withholding their votes and certificates (live without one; stalled until one returns with two). Every phase asserts identical blocks and state roots at every height. Pending: the 2-week soak, and the equivocating-leader, wrong-`exec_root` and junk-tx scenarios, which come with P-STAKE's evidence and junk-charge paths.
- ✅ **Integrated (wave 3, mainnet-prep):** the nine work packages run as one node. The simulator's equivocating validator (no slashing protection) is reported and slashed identically on every node (`an_equivocating_validator_is_slashed_identically_everywhere`), and junk leaders and offline validators are charged, jailed and come back (`junk_leaders_and_offline_validators_are_jailed_and_come_back`). `state_machine` drives the integrated chain (issuance, staking, governance, beacon and fee-market txs), and a 10th target, `ghost_tx`, covers Ghost Mode's wire form. Pending: the 2-week soak and a wrong-`exec_root` scenario.
- ✅ **Polish (mainnet-prep):** an 11th fuzz target, `evidence` (`ReportEquivocation`'s bytes: canonical decoding of the three fault kinds, verification never panics, verified evidence slashes and tombstones exactly once with the invariants holding; 186,811 executions in 2 minutes on nightly-2026-10-06, no finding). Simulator scenarios: a leader citing a wrong `exec_root` has none of its blocks finalized, the chain stays live and it's jailed for the slots (`a_leader_citing_a_wrong_exec_root_is_rejected`), and the spam load test (TOK-2). Pending: the 2-week soak.
- ✅ **Audit fixes, round 2 (supply-chain-B-1):** the nightly fuzz job runs in a public repository, so its crashes stay private. The fuzzer's output goes to a file, never the log, and a crash shows only as `Fuzz <target>: crash found`. Crash files leave the runner only age-encrypted to the maintainers' keys (`FUZZ_CRASH_AGE_RECIPIENTS`; unset means nothing is kept). Open findings' inputs live outside the tree (`node/fuzz/private/`, `BLOCKULA_FUZZ_FINDINGS`) and are handled as private advisories (SECURITY.md). `scripts/check-fuzz-workflow.sh` and `scripts/test-fuzz-seal.sh` run in CI.

**SEC-4. Public HTTP reads can stall consensus.**
- **Missing:**
  - Every handler locks the same `Mutex<Chain>` that propose, verify and execute use.
  - Several handlers do O(state) work under that lock:
    - `/api/status` recomputes the flat state root (`api.rs:396`).
    - `/api/key/{id}` scans every account (`api.rs:612`).
    - `/api/account` scans every name and hunt (`api.rs:581, 603-604`).
    - `/api/sync` reads up to 8 MiB from disk (`api.rs:880-944`).
  - Only `POST /api/tx` and the faucet are rate limited (`api.rs:478, 666-673`).
  - The "Become a validator" guide has validators advertise a public HTTP address (README.md "Become a validator"). Full nodes forward txs to validators over HTTP (`api.rs:192-218`).
- **Why it blocks:** a modest request rate against a validator's HTTP delays its votes. Doing that to a third of the set halts the chain.
- **Done when:**
  - Validators don't expose HTTP publicly by default. Sentry or RPC full nodes sit in front.
  - Reads run against a snapshot of state published after each block (or the store from CV-1), never under the consensus lock.
  - Reads have per-client rate limits and timeouts.
  - A load test shows finalization is unaffected at a stated request rate.
- **Effort:** M. **Who:** Team.
- ✅ **Code side (wave 2):** every read handler serves the view the chain publishes after each block (an O(1) state clone plus a database snapshot), never the consensus lock; nothing scans state per request (owner, key, creator, claimant and voucher indexes in the database; rankings computed once per block); per-IP token buckets on reads (`--read-rps`, `--read-burst`) and a timeout on every route (`--http-timeout-secs`). Tests show every read completes while the chain lock is held and blocks execute normally under thousands of concurrent reads. Pending: validators' HTTP private by default behind sentries, and the load test against a running network.

**SEC-5. No vulnerability disclosure program.**
- **Missing:** CONTRIBUTING.md "Security" points to GitHub Security Advisories, and that's all. There's no SECURITY.md, no contact, no response timeline and no bounty.
- **Done when:** a SECURITY.md gives scope, contact and timelines, and a funded bounty (self-run or through a platform) has been live on the incentivized testnet for at least a month before genesis. ✅ SECURITY.md exists (private advisories, response targets, testnet safe harbor), and the program is written (docs/BUG_BOUNTY.md: scope, severities, safe harbor, disclosure). Pending: funding it and running it on the incentivized testnet.
- **Effort:** S, plus a bounty budget. **Who:** Team.

### Cryptography & networking

**CRY-1. The p2p transport isn't post-quantum.** (known)
- **Missing:** Commonware's handshake authenticates peers with ML-DSA-65, but the session key comes from X25519 and traffic is encrypted with ChaCha20-Poly1305 (PLAN.md "Known limits"; `/api/status` says so, `api.rs:414`). Meanwhile README.md says "no elliptic curves anywhere".
- **Why it blocks:** recorded validator traffic can be decrypted later, including the mempool and which IP sent which tx. More importantly, the headline claim is false at launch unless this lands.
- **Done when:**
  - The Commonware stream handshake uses a hybrid X25519 + ML-KEM-768 exchange, with both secrets fed into the KDF and the transcript bound. It's upstreamed, or carried as a pinned, reviewed fork.
  - Downgrade and interop tests pass, and the change is in SEC-1's scope.
  - Alternatively, a recorded decision (DEC-9) to launch without it, with README and ONE_PAGER corrected.
- **Effort:** L. **Who:** Team, Upstream, Auditor.
- ✅ **Bound to the build (audit #1/#3):** the node depends on the vendored `commonware-stream` directly and builds `/api/status`'s `crypto.p2p_transport` from constants only the hybrid module exports, so a build where the `[patch.crates-io]` stops applying fails to compile instead of linking the classical handshake; a test fails if the lockfile holds a second, registry copy.

**CRY-2. Fast sync is weakly subjective, and the genesis keys sit on one laptop.** (known, plus the key detail)
- **Missing:**
  - A joiner trusts its newest trusted root (the genesis set, or a checkpoint's pinned set) plus 2f+1 handoff signatures for every set change after it (`epochs::verify_from`; PLAN.md "Known limits"). Keys of a long-gone set can sign a fake handoff, even retroactively.
  - The epoch anchor a node fast-syncs into comes from the peer and isn't certified (`snapshot.rs:266-277`).
  - Every testnet genesis key was generated on one machine (`deploy/launch.sh:71`). Whoever holds that machine can forge an alternate history for any fresh joiner, forever.
  - `join --genesis <URL>` without `--genesis-hash` trusts whatever that URL serves, and only prints a warning (`node.rs:390-405`).
- **Why it blocks:** new nodes, exchanges and RPC providers can be fed a fake chain.
- **Done when:**
  - Each release ships a signed checkpoint (height, block hash, validator-set hash). `join` requires it by default.
  - The weak-subjectivity period is documented and no longer than the unbonding period (CV-3).
  - The epoch anchor is certified in the snapshot manifest.
  - The mainnet genesis hash is compiled into the binary for the mainnet chain id.
  - Genesis keys are generated by independent operators (OPS-1).
- ✅ **Code side (wave 3, P-SYNC):** each binary embeds a trust table per known chain id (`node/checkpoints/*.json`, compiled in and attached to the signed release): the genesis hash and checkpoints `(height, block hash, validator-set hash)`. `blockula-1`'s entry is a placeholder until the ceremony, so every binary refuses mainnet until the launch release fills it in. `join` requires `--genesis-hash` or a known chain id (no more warn-only), takes `--checkpoint HEIGHT:HASH[:SET_HASH]`, and refuses any genesis, snapshot, epoch anchor or sync batch that contradicts a checkpoint; a pinned set defeats retroactive handoffs from old keys (test `a_retroactive_handoff_forgery_needs_only_old_keys_and_a_checkpoint_stops_it`). The fast-sync manifest certifies the epoch anchor with a finalization from the previous epoch's set. The weak-subjectivity period is half the evidence window, which is at most the unbonding period (~10.5 days at genesis): an empty home refuses to sync from an older root unless `--allow-stale-checkpoint`, and `/api/status` shows `checkpoint_height` and `weak_subjectivity_blocks`. `blockula checkpoint` computes a checkpoint that several independent nodes agree on; OPERATIONS.md "Weak subjectivity" has the per-release and weekly signed checkpoint process. Pending: genesis keys from independent operators (OPS-1), the ceremony's hash, and the first release checkpoints.
- ✅ **Integrated (wave 3, mainnet-prep):** `blockula validator init` checks the genesis it fetches the way `join` does: a known chain's genesis must match the release, `--genesis-hash` must match, and a genesis fetched from a node needs the pin (`validator_init_checks_the_genesis_pin`). `run_validator` keeps the trust table alongside P-UPGRADE's halt control and slashing protection.
- **Effort:** M. **Who:** Team.
- ✅ **Audit fixes (fix-sync):** a validator signs a handoff only for a set change its own executed (or certified) state shows on both sides, and the handoff message binds the outgoing set's hash too (`BLOCKULA_HANDOFF_V2`, now V3 with the genesis hash, below), so a signature is a quorum share for exactly one transition; a fast-synced node adopts only the history it verified (its trusted root through the manifest's last epoch, checked against the certified state's sets), a genesis home ignores a saved `epochs.json`, and a node drops history past the epoch it executed (F08: `only_executed_transitions_are_signed_and_signatures_bind_the_outgoing_set`, `only_the_verified_history_is_adopted_from_a_manifest`, `history_past_the_executed_epoch_is_dropped_on_open`). The history no longer rides in manifests: `/api/epochs?from=` serves ~2 MiB pages (cached per registry), joiners verify from their newest trusted root, nodes keep the weak-subjectivity window and trim older changes past 8 MiB, and the handoff exchange asks only while a change lacks a quorum and verifies, off the chain lock, only signatures it lacks (F10, F19/F26: `history_is_paged_within_a_budget_and_verifies_from_a_pinned_root`, `merging_verifies_each_signature_once_and_stops_at_a_quorum`). `/metrics` has `blockula_epochs_known_through`, `blockula_epochs_proven_through` and `blockula_epochs_from`.
- ✅ **Polish (mainnet-prep):** a pruning node's window always holds the epoch anchor its manifests certify (`chain::min_keep_blocks` covers an epoch plus both kept snapshots; `the_smallest_window_keeps_the_epoch_anchor` fails on the old window), and a certificate execution didn't get from consensus (fetched by marshal from peers, from before a restart) is read back from marshal's store and kept for epoch ends and checkpoints (`consensus::fill_late_certs`, `Chain::store_late_cert`).
- ✅ **Audit fixes (fix-sync, fast-sync availability):** a node keeps two long-lived snapshots besides its two newest (the first it wrote in each of the last two ~15-minute stretches, `snapshot::long_interval`) and serves a state over 32 MiB from the newest long-lived one, so a joiner has at least 15 minutes to fetch the chunks, and the smallest pruning window covers every kept snapshot and the blocks after it (F63: `served_snapshots_outlive_a_download`, `a_served_snapshot_outlives_newer_ones`); `?min=` serves one that reaches the joiner's checkpoint. Joiners try peers in a random order, spread chunk requests over every peer holding the snapshot, drop a peer that stalls (30 s a chunk) or fails one, prefer peers faster than 10 s a chunk, and give up on a manifest after 2 s a chunk plus 2 minutes (F62: `a_stalling_chunk_server_is_abandoned`, `peers_are_asked_in_a_new_order_each_run`). What's left is in PLAN.md "Known limits" (fast sync's time budget).

- ✅ **Audit fixes, round 2 (r2-sync):** handoffs bind the chain instance: `BLOCKULA_HANDOFF_V3` signs the genesis hash beside the chain id, epoch and both sets' hashes (`HANDOFF_FORMAT` 3, in every sign, verify and merge path), so a relaunch under the same chain id shares no handoff with the old chain (F02, review-integrate-compose-1: `a_handoff_for_another_genesis_of_the_chain_id_does_not_verify`, `handoffs_do_not_replay_across_a_relaunch`). A fast-synced node adopts only the signatures that verified (a quorum per change) and nothing past the certified epoch, so a peer's junk never displaces a valid signature in what it serves (review-fix-sync-2, -5: `only_verified_signatures_and_epochs_are_adopted`, `junk_and_entries_past_the_certified_epoch_are_not_adopted`). A chain upgraded in place to a new handoff format restarts its history at the oldest set its state holds, since older changes can't be signed again; relaunched chains (testnet-2, mainnet) start at format 3 (review-fix-sync-4: `a_handoff_format_upgrade_restarts_the_history_at_the_oldest_held_set`). Fast sync has one deadline per peer over the history and the chunks (2 minutes plus 2 s per epoch, at most 30 minutes, plus the download's budget), refuses a manifest past the chain's expected height before fetching history for it, and refuses history pages that make no progress (F62, review-fix-sync-1: `a_peer_paging_history_forever_loses_the_attempt`); a peer with no snapshot reaching `?min=` serves its furthest one, so a joiner whose checkpoint is newer waits for the next snapshot instead of replaying from the genesis (review-fix-sync-3). HTTP sync judges peers against each other: it keeps to the fastest, explores every 8 rounds, starts at a random peer, and benches a round a block time long that is 4× slower than another peer's recent best, a failed round, or a stall before "nothing new" (F27: `a_trickling_peer_does_not_capture_sync` with a peer just over twice the chain's rate, `a_peer_just_above_the_chain_rate_loses_to_a_fast_one`). `--client-ip-hops` counts entries across every line of the header (F29). The weak-subjectivity period follows governance: nodes enforce the shortest of the genesis period, the release's recorded `weak_subjectivity_blocks` and their own state's (gap-6-1: `the_weak_subjectivity_period_follows_governance`); a joiner on a release older than a shortening still needs a checkpoint younger than the new period (PLAN.md "Known limits").
- ✅ **Audit fixes, round 3 (r3-sync):** the evidence window has a protocol floor of two weeks (`params::EVIDENCE_WINDOW_FLOOR_DAYS`, a band on `evidence_max_age_epochs` checked when a `ParamChange` is proposed and when it runs, and at mainnet's genesis; unbonding can't be shorter than the window), so the weak-subjectivity period never falls below a week. Before it syncs, a joiner (`join`, and every full-node start, which waits for a peer while its home is empty) reads `weak_subjectivity_blocks` from every peer's `/api/status` and enforces the shortest, never below the floor, and refuses a root too old for it, naming the peer (gap-6-1: `a_joiner_heeds_the_period_its_peers_report`, `the_weak_subjectivity_period_follows_governance`, `the_evidence_window_has_a_floor`, `the_evidence_window_never_falls_below_its_floor`). HTTP sync measures a round over at least a quarter block time, in blocks and bytes, so a tiny round answered at once can't bench a full one; a peer with nothing new loses its rate; a peer benched only for being slower keeps its rate as the bar and is free again when every free peer has nothing or a short round falls 4× below it (review-r2-sync-1: `a_fast_tiny_round_then_empty_answers_does_not_capture_sync`, `hostile_peers_cant_hold_the_turn_after_benching_an_honest_one`, `a_bar_is_only_what_a_peer_really_delivered`, virtual-time simulations of the real rotation).
- ✅ **Audit fixes, round 4 (r4-node):** a root's age no longer counts every slot the chain ever missed. Checkpoints record their block's `timestamp_ms` (`HEIGHT:HASH:SET_HASH:TIMESTAMP_MS`, printed by `blockula checkpoint`, required of embedded ones; the older forms still parse), and the chain's expected height is counted from the newest block whose time the node trusts (that checkpoint, a synced node's own head, or the genesis), so on an aging chain one peer's floor-sized report can't refuse a checkpoint taken at the tip; an empty home whose newest checkpoint has no time reads it from a peer's copy of the block, which its hash covers (`an_untimed_checkpoint_counts_from_its_blocks_time`). The time is checked like the hash: a block at that height with another time, a later block earlier than it allows, and a time below the genesis' line or past the clock are refused (review-r3-sync-1: `an_aging_chain_measures_a_checkpoint_from_its_own_time`). A queued shield's refusals, and a same-note spend's, no longer name a tip past the newcomer's cap: they say to wait until it's included or leaves the mempool (review-r3-consensus-1: `a_queued_shield_is_its_senders_last_tx`, `a_same_note_replacement_never_names_a_tip_past_the_cap`).

### Consensus, state & validator set

**CV-1. The state layer doesn't scale and can't produce proofs.**
- **Missing:**
  - All state is in-memory `BTreeMap`s (`chain.rs:400-428`).
  - The state root is a flat BLAKE3 over all of it, with structs serialized by serde_json (`chain.rs:1029-1077`). It's recomputed for every executed block, every proposal (`consensus.rs:281, 296`) and every `/api/status` call (`api.rs:396`). PLAN.md "Known limits" puts the cost at ~10 ms per 100k accounts.
  - State isn't persisted. A validator restart re-executes every block since genesis (`chain.rs:1403-1512`).
  - The tx index and per-account history are unbounded in-memory maps (`chain.rs:1278-1279`).
  - Every 100 blocks, a new thread clones the whole state and writes it as one JSON blob (`chain.rs:1826-1833`, `snapshot.rs:61-63`). Snapshots are capped at 4 GiB (`snapshot.rs:32`).
  - There's no state rent or deposit, though PLAN.md "Tokenomics" promises it.
  - The root already needs compatibility branches for older chains (`chain.rs:1044-1075`).
- **Why it blocks:**
  - **Cheap DoS.** A new account costs one minimum fee (~64k drops) plus 0.01 FANG moved into it (`types.rs:682`). At ~388 txs per block, about 1.4 hours and ~130 FANG of fees create 2M accounts. That likely exhausts a 512 MB validator (`deploy/launch.sh:126-127`) through state plus indexes. At 10M accounts (~650 FANG, ~7 hours), the root alone takes ~1 s per block. That's past the 1 s block time and the checkpoint wait (`consensus.rs:416-433`). See the appendix for the numbers.
  - **Restarts get slower forever.** Upgrades restart every validator at once (`deploy/launch.sh:131`), so the whole chain is down for the full replay.
  - **No light clients.** Without Merkle proofs, wallets must trust one RPC (WAL-4).
  - **Hard to change later.** The state root and encoding are consensus rules, so changing them after genesis is a hard fork.
- **Done when:**
  - State lives in a disk-backed authenticated store with incremental roots and inclusion proofs. commonware-storage's `qmdb` and `merkle` modules are already in the pinned dependency set.
  - State uses a canonical binary encoding.
  - State is committed per block, atomically with the block, and restart time doesn't depend on history length.
  - The tx and history index moves to disk or to a separate indexer (PLAN.md "Roadmap": "Remaining: a standalone indexer").
  - Snapshots stream instead of being built in memory.
  - Accounts, names and other records pay deposits or rent (DEC-6).
  - A benchmark at 10M accounts shows execute plus commit well under the block time on the reference validator spec.
- **Effort:** XL. It's new storage and a new root, every module migrates, and it must land before the audit. **Who:** Team.
- ✅ **Wave 1 (framework):** state maps are tracked `imbl` maps (O(1) clone), every record has a canonical borsh encoding, and the root is a sparse Merkle tree updated per block from the touched keys, with inclusion and exclusion proofs (`state/`). Snapshots are canonical records, decoded as a stream.
- ✅ **Wave 2 (persistence, P-STATE-B):** records, tree nodes, indexes and the commit point are written per block in one redb transaction, after the block logs are fsynced and before consensus is acknowledged (`store.rs`). A restart loads the database and checks it against the tree and the log, then executes only blocks logged past its commit point: ~0.7 s at 1M accounts, whatever the history (`restart_time_at_1m_accounts`). The tx index and account history are on disk; `/api/proof/{namespace}/{key}` serves inclusion and exclusion proofs; snapshots stream both ways (the writer cuts chunk files as it compresses, a joiner checks each chunk and decodes from a file). Pending: the 10M-account execute-plus-commit benchmark. ✅ DEC-6 (P-ECON): opening an account burns `account_creation_fee` (0.1 FANG), and names renew yearly.
- ✅ **Integrated (wave 3, mainnet-prep):** the state schema is final at `SCHEMA_VERSION` 4 (staking, governance, beacon, econ, upgrade and Ghost Mode records; 5 since the polish pass: the fee slots also fix Ghost Mode's per-block limits `FEE_LAG` blocks ahead, so a `ParamChange` can't make verifiers at different heights disagree; 6 with the audit fixes, one version for all of them: `chain_params` gains `tip_cap_multiple`, staking's slash bookkeeping (`slashed_from`, entries by validator, epochs' highest views), the governance scalars' recent spends, vote sweep and multisig sweep cursor, `Distribution`'s id, `Params::bootstrap_excluded` and `NameRecord::offered_to`; 7 with the second fix round, again one version for every package: `chain_params` gains `bootstrap_commission_cap_bps`, pools `ready_at`, liveness rings `max_missed`, the `upgrade` record its withdrawals, `Distribution::proposal`, `NameRecord::grace_blocks`, and Proof of Contribution's withdrawn vouches and handle holds, namespaces 26 and 27, and the round's action encodings (`AddKey`'s proof of possession, the `Vote` and `CommitVotes` digests), which multisig proposals store; `STORAGE_VERSION` `prunable-v8`; 8 with the third round: pools gain `key_update_at` (F04's once-an-epoch limit, apart from the readiness record) and `admit` (the candidate a member of a set of one or two admitted), and `Undelegate` gains `amount`, which a pending multisig `Undelegate` proposal stores; `STORAGE_VERSION` `prunable-v9`; 9 with the fourth round: the `upgrade` record's withdrawals keep the highest superseded version (`Withdrawals::superseded`); `STORAGE_VERSION` `prunable-v10`). Proposals and multisig proposals store their kind and action in the tx encoding, so changing an action's or a proposal kind's encoding changes stored state and the block logs, and bumps both versions; a state test pins every vector action's stored form to `SCHEMA_VERSION` (audit review-r3-wallet-2). The golden root was recomputed and checked by an independent JavaScript implementation (`@noble/hashes` BLAKE3), and the proof vectors and fuzz seeds were regenerated.

**TOK-2. The fee market is a fixed price with first-come ordering.**
- **Missing:** the minimum fee is a constant, `10_000 + 10 × bytes` (`types.rs:613-615`). Blocks fill in arrival order. Each validator keeps its own 5,000-tx mempool and evicts by fee per byte only when full (`chain.rs:1943-1955, 2067`).
- **Why it blocks:**
  - A transfer is ~5.4 KB (minimum fee ≈ 64k drops) and ~10.8 KB as JSON, so ~388 fit in a 4 MiB block.
  - Filling every block for a day costs ≈ 2,200 FANG.
  - Honest users have no predictable way to outbid spam.
  - The fee can only change by hard fork.
- **Done when:** a per-byte base fee adjusts with block fullness (and is burned), and the tip buys priority. A spam load test shows honest txs confirm within a bounded number of blocks at a bounded cost. Fee parameters are either changeable by governance (GOV-1) or fixed by decision.

- ✅ **Admission (audit #10, wave 3):** the mempool dry-runs every tx after its sender's queued txs, as a block would, so txs that can never execute (behind a `RemoveKey`, past a session limit) no longer hold slots for free; each sender's simulation is cached, so admission stays one dry run per tx with a full mempool. Pending: the fee market itself (P-ECON).

- ✅ **Polish (mainnet-prep):** the spam load test runs on the real consensus path (`spam_doesnt_delay_honest_txs_with_a_competitive_tip`): with 64 KiB blocks and 150 zero-tip spam transfers queued (~12 full blocks of backlog), txs under the base fee aren't admitted, and honest transfers priced as wallets price them (`/api/fees` suggested + a tip) each confirm within 3 blocks (1 in the run) while the backlog is still pending, charged their block's base fee plus the tip, never more than offered; the full blocks raise the base fee (4× the floor here).

## 3. Should-fix before launch (not strictly blocking)

**SF-1. Predictable leaders.**
- **Missing:** `RoundRobin` (`consensus.rs:785`) publishes the leader schedule, and validator p2p addresses are public in genesis. That makes it cheap to DoS whoever leads next.
- **Done when:** the leader order is seeded per epoch from CRY-3's beacon, and sentry nodes hide validator IPs.
- ✅ **Leader order (wave 3, P-BEACON):** each epoch's elector is Commonware's `RoundRobin::shuffled` with a seed derived from that epoch's beacon value (`consensus::elector`). Validators reveal in the second half of the previous epoch, so the order is known at most half an epoch ahead. `consensus::leader` elects the same way from state, for downtime accounting; the simulator checks every proposer against it (`beacon_rounds_seed_the_leader_order`). The shuffle is the pinned Commonware's (`=2026.9.0`), and downtime slashing depends on it, so a Commonware upgrade that changes `RoundRobin::shuffled` is a hard fork. Pending: sentries.
- **Effort:** M.

**SF-2. Clock skew.**
- **Missing:** a block more than 1 s ahead of the verifier's clock is rejected (`consensus.rs:54, 358-360`). A validator whose clock lags by over 1 s can't vote, and nothing measures skew.
- **Done when:** operator docs require NTP, skew has a metric and an alert, and the tolerance is set using a simulator test with skewed clocks.
- **Effort:** S.
- ✅ **Simulator (wave 3):** `sim/byzantine.rs` runs one validator 600 ms ahead (its blocks are accepted), 3 s ahead (the others refuse its blocks) and 3 s behind (it refuses theirs, so it doesn't vote, yet keeps executing what the other three finalize); the chain stays live and agreed throughout. With 1 s blocks, a 1 s bound is about one block of tolerance.

✅ **SF-3. Binary tx and block encoding.**
- **Missing:** txs travel and are stored as hex JSON (`consensus.rs:71-86, 312`). That's about twice the binary size fees are priced on (`types.rs:592-594`), and the JSON isn't canonical (CV-5).
- **Done when:** a canonical binary encoding replaces it. This is a consensus format: change it before the freeze or live with it.
- **Effort:** M.
- ✅ **Done (wave 1):** the Tx v3 wire form (`Tx::to_bytes`, strict `Tx::from_bytes`) in CBlock v2 blocks and gossip; fees price its length; JSON stays the API format.

**SF-4. Execution holds the global lock through fsync and mempool revalidation.**
- **Missing:** `execute` appends and fsyncs two files, recomputes the root and re-applies up to 5,000 mempool txs (`chain.rs:1735-1782, 1874-1905`). Every API call and every consensus verify waits for it.
- **Done when:** I/O and revalidation run outside the lock, and latency is measured.
- **Effort:** M (overlaps CV-1 and SEC-4).
- ✅ **Done (wave 2):** on the consensus path the chain lock covers only in-memory execution; appending and fsyncing the logs, the database commit and the mempool check (on an O(1) state copy) run without it, and readers never take it (`blocks_are_written_without_the_chain_lock`, `heavy_reads_dont_slow_block_execution`). Validators also prune: they keep about two days of blocks (`--prune-blocks`, `--archive`), deleting whole log segments behind the window (OPERATIONS.md, Disk sizing).

✅ **SF-5. Snapshot threads can pile up.**
- **Missing:** each checkpoint spawns a new thread holding a full state clone (`chain.rs:1826-1833`). If writing takes longer than 100 blocks, threads accumulate.
- **Done when:** one snapshot worker handles every checkpoint and skips while busy. ✅ Done: a checkpoint is skipped (with a warning) while the previous snapshot is still being written.
- **Effort:** S.

✅ **SF-6. Release builds don't check overflow.**
- **Missing:** `node/Cargo.toml` has no `[profile.release]`, so `+=` and `-=` on balances and supply wrap silently (`chain.rs:162-163, 508, 537, 698-699`).
- **Done when:** release builds set `overflow-checks = true`, or every balance and supply path uses checked arithmetic, with tests. ✅ Done for the node crate (`[profile.release.package.blockula]`); checked arithmetic on balance paths is still worth doing.
- **Effort:** S.

**SF-7. One misconfiguration turns off every rate limit.**
- **Missing:** loopback callers are never limited (`api.rs:105, 671`), so a reverse proxy on localhost without `--client-ip-header` disables every limit. Limits are also in memory and per node (PLAN.md "Known limits").
- **Done when:** nothing is unlimited by default, and the node warns at startup when it looks like it's behind a local proxy.
- **Effort:** S.

**SF-8. Closed records live forever in the root.**
- **Missing:** hunts, claims, Séances, grants and every validator registration are never pruned, and are hashed into every block (`chain.rs:1045-1075`; `poc.rs:312-339`). Some admission checks scan every claim (`poc.rs:347-349, 715`).
- **Done when:** archived records leave the hot state (with CV-1), and admission is O(log n).
- **Effort:** M.
- ✅ **Polish (mainnet-prep):** the epoch-boundary PoC steps (refunding stale claims, opening Séances) walk an index of open claims instead of every claim ever made.

**SF-9. Names: renewal, transfer and pricing.**
- **Missing:** there's no renewal, though PLAN.md "Tokenomics" promised it for Phase 1. There's no action to transfer or release a name (`types.rs:32-156`). Prices are fixed in FANG (`types.rs:618-624`). Adding renewal after genesis changes the terms for existing holders.
- **Done when:** renewal, transfer and pricing are decided (DEC-11) and built before genesis.
- **Effort:** M.
- ✅ **Wave 3 (P-ECON):** names cost `name_price_3/4/5` (100, 25, 5 FANG, to the treasury) and last a year; `RenewName` adds years at 20% of the price each, at most 10 years ahead; an expired name doesn't resolve, and for 30 days only its owner can renew it, then anyone can register it; lapsed records are swept a few per block. `TransferName` and `ReleaseName` work; genesis reserved names can't be registered. Pending: assigning reserved names by governance (DEC-11).
- ✅ **Audit F34:** an unsolicited `TransferName` could make any name, registered earlier than the victim's own, the victim's displayed identity (or, eight of them expiring, hide it). A transfer is now an offer the recipient must accept (a `TransferName` to itself), and accepting re-stamps `registered_at`, so an accepted name never ranks ahead of names the account registered itself (`a_name_changes_hands_only_when_its_recipient_accepts`). `/api/name` shows `offered_to`; the SDK has `acceptName`/`withdrawNameOffer`, the CLI `blockula name accept|withdraw`.
- ✅ **Audit gap-6-3:** a name's grace end wasn't stored: `grace_until` was `expires_at` plus the live `name_grace_blocks`, so a `ParamChange` lowering it (bounds allow 0) made every name already in its grace registrable in the next block, its owner unable to renew and the sweep free to delete it. `NameRecord` now keeps `grace_blocks`, the parameter when it was registered or last renewed, and its grace is the longer of that and today's value (`econ::grace_until`, used by `RegisterName`, `RenewName`, the sweep and `/api/name`): lowering the parameter shortens only the grace of names registered or renewed after it (`lowering_the_grace_keeps_the_grace_names_were_promised`). State schema 7 covers the field; the SDK's `decodeName` reads it.
- ✅ **Audit F35 (mitigated, accepted risk):** a registration seen in the mempool could be outbid with a higher tip (or put behind the proposer's own), leaving the first asker without the name. Mempools now give a name to whoever asked first: another account's `RegisterName` for a name that an includable registration has waited on for at most `NAME_HOLD_BLOCKS` (17) isn't admitted, whatever its tip (`Chain::first_to_ask`, a name index kept with the mempool; `a_name_goes_to_whoever_asked_first`). What's left is a proposer ordering its own registration first, or a race to a node the first asker's tx hasn't reached yet: PLAN.md "Known limits". Commit-reveal registration would close it at the cost of a second tx and a wait per name; not before genesis. Fix review: the hold saw only a top-level `RegisterName`, so a 1-of-1 multisig's `MultisigPropose { RegisterName }` (or the `MultisigApprove` that runs a stored one) got past it, and a multisig's own waiting registration held nothing against tipped ones (its owner keys can't tip). Every form now asks for the name (`econ::name_asked_for`, the approval's stored proposal looked up at admission) and is held off; a waiting one holds the name while it would register it in the next block (`governance::runs_when_included`; `wrapped_registrations_ask_first_too`).

**SF-10. Full nodes can't use p2p.**
- **Missing:** discovery only admits tracked validators (PLAN.md "Network and sync"), so full nodes sync and forward over HTTP. Every testnet validator's `http_addr` is the one public RPC (`deploy/launch.sh:74-76`).
- **Done when:** a documented sentry architecture exists, or full nodes are admitted as secondary peers.
- **Effort:** L.

**SF-11. No multisig accounts or scoped session keys.**
- **Missing:** any one owner key fully controls its account (`chain.rs:628-666`). Session keys can't be limited to particular modules (PLAN.md "Accounts"). Treasuries, foundations and exchanges need M-of-N.
- **Done when:** M-of-N accounts exist (GOV-1 needs a minimal version anyway) and session keys can be scoped.
- **Effort:** M.
- ✅ **M-of-N (P-GOV):** `MultisigCreate` makes an account M-of-N over its owner keys; its owner keys then only sign `MultisigPropose`/`MultisigApprove` (enforced at admission), the threshold-th approval runs the action as the account, proposals expire, and key changes can't drop the owners below the threshold. Session keys keep working within their limits. Pending: module-scoped session keys.
- ✅ **Audit fix (F01):** one owner key of an M-of-N multisig could empty the account through the tip of a `MultisigPropose`. A multisig's owner keys act alone in those txs, so they carry no tip (session keys still tip within their limit) (`a_multisig_owner_key_cant_tip`).

**SF-12. Secret material isn't zeroized.**
- **Missing:** seeds sit in plain byte arrays (`crypto.rs:55-58`; `pq.rs:124-128`).
- **Done when:** key types use `zeroize`, and key files can optionally be encrypted at rest.
- **Effort:** S.

**SF-13. Contribution attestations depend on validators' balances and GitHub tokens.**
- **Missing:** attestation fees come from each validator's consensus-key account. If a third of the set can't pay, claims never settle (PLAN.md "Known limits"). Each validator also needs a `GITHUB_TOKEN` (`github.rs:15-17`). For the testnet, `deploy/set-github-token.sh` sets it on every app (public-read-only tokens only).
- **Done when:** the attestation fee payer is configurable (or attestations are fee-free with a cap), and each operator's token handling is documented.
- **Effort:** S.
- ✅ **Wave 3 (P-STAKE):** a validator's consensus key may sign its system txs (`attest_claim`, `attest_revert`, `beacon_commit`/`beacon_reveal`, `report_equivocation`, and `update_validator`, whose target only the signer can name) with `from` = its owner, who pays; admission allows exactly that (`staking::system_tx_key`). Nodes pay from the owner when it's a separate account and from the consensus key's own account otherwise; `BLOCKULA_SYSTEM_FEES=self` forces the latter. The GitHub token is in OPERATIONS.md (a public-read-only `GITHUB_TOKEN` in `/etc/blockula/env`).
- ✅ **Integrated (wave 3, mainnet-prep):** beacon duties, revert attestations and evidence reports all go through `submit_system`, which signs with the consensus key and pays from the owner, and multisig owners' validators still sign their system txs (`a_multisig_owners_validator_still_signs_its_system_txs`).
- ✅ **Audit fixes (F04, F06, F11):** a consensus key signing for its owner could set any tip, so a stolen hot key moved the cold owner's whole balance (multisig or vesting owners included) to the proposer, itself in its own slot. Those txs carry no tip now; the owner pays only the base fee (`a_consensus_key_cant_tip_its_owners_fang`). Duties wait only while the node is behind a finalized height it verified (`Chain::syncing`): peers' claimed tips are display-only, and a lying majority of HTTP peers used to keep a validator from revealing until it was jailed (`lying_peers_cant_hold_back_validator_duties`). Second round: what a stolen consensus key can burn is bounded by the validator's duties: such a tx whose action fails isn't admitted, it updates the validator for its owner once an epoch, and a tombstoned or removed validator's key signs only a reveal it owes (`a_stolen_consensus_key_burns_at_most_its_validators_duties`). The residual (a few base fees an epoch, besides double-signing) is in PLAN.md "Known limits".
- ✅ **Audit fixes (third round, schema 8):** a validator's terms are its owner's call. Its consensus key changed them from the validator's own account (where it's the implicit owner key) when the owner was another account, past a multisig owner's approvals and F04's once-an-epoch limit, and could unjail it there; it updates the validator only for its owner now (once an epoch, through the multisig's gate), and `Unjail` is the owner's alone (review-r2-integrate-compose-1: `staking::owned_validator`, `a_consensus_key_changes_its_validators_terms_only_for_its_owner`, `a_multisig_owners_validator_still_signs_its_system_txs`). A small set's readiness is its own action, `ValidatorReady { epoch }` (tag 60), which writes the readiness record and nothing else: round 2's "no-op" `UpdateValidator` carried the commission its node read, so it reverted an owner's queued change and wrote a lowered cap over the owner's setting (review-r2-staking-1: `readiness_leaves_the_owners_terms_alone`). It and `AdmitValidator { validator, epoch }` (tag 61) are lane duties while they'd apply (at most one candidate an epoch, once; each of the set's one or two members once), so the node's readiness never holds the beacon duties behind it out of the lane (review-r2-consensus-2: `a_readiness_queued_ahead_of_a_reveal_keeps_it_in_the_lane`). Both are SF-13 system txs: a multisig owner's validator sends them without `BLOCKULA_SYSTEM_FEES=self`.

✅ **SF-14. Operator documentation.**
- **Missing:** there's no reference hardware spec, port and firewall guide, NTP requirement, disk sizing or sentry setup.
- **Done when:** all of those are documented and the commands work.
- **Effort:** S–M.
- ✅ **Done (wave 1):** docs/OPERATIONS.md (hosting, hardware, bandwidth, disk sizing, ports and firewall, time, sentries, keys, upgrades, incidents, runbooks).

✅ **SF-15. The explorer has no CSP.**
- **Missing:** the explorer is served from the API's origin (`api.rs:259`). It escapes on-chain strings consistently (`esc()` in `explorer.html`), but sets no CSP.
- **Done when:** the node serves the explorer with a CSP.
- **Effort:** S.
- ✅ **Done (audit F64):** the hash router resolved `#/constructor/…` to `Object`, which handed the route id to `innerHTML` unescaped (a DOM XSS on the node's origin). Routes now resolve against the explorer's own views only and only strings reach `innerHTML`; `GET /` sends a CSP that runs only the explorer's inline script (by its SHA-256), fetches from its own origin only and can't be framed (`explorer_routes_only_to_its_own_views` runs the page script under Node, `explorer_is_served_with_a_script_hash_csp`, and the wallet e2e's `explorer.spec.ts`).
